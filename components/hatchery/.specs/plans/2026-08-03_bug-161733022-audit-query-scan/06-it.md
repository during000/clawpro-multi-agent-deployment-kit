## MySQL 8 Schema 与增量迁移

### 全新初始化

使用当前 `sql/init.sql` 创建 `audit_v4_fresh`，随后执行一次当前增量迁移验证幂等性。`audit_logs` 最终包含：

- `idx_audit_logs_identifier_user_id(identifier, user_id)`

- `idx_audit_logs_identifier_resource_id(identifier, resource_id)`

`information_schema.statistics` 显示三组联合索引均以 `identifier` 为第 1 列、目标筛选字段为第 2 列。

结果：PASS。三个联合索引均创建成功，结构与全新初始化一致；第二次执行走 `SELECT 1` 幂等分支，无重复索引错误。迁移仅包含 ADD INDEX，不包含 DROP INDEX。

## 执行计划

在全新库写入 10,000 条样本：`tenant-a` 7,000 条、`tenant-b` 3,000 条，覆盖 200 个用户、500 个资源。该数据只验证索引选择，不代表生产数据分布或生产延迟。

### Count

| 查询 | MySQL 选用索引 | 估算扫描行 | Extra |
|------|----------------|-----------:|-------|
| `identifier = tenant-a` | `idx_audit_logs_identifier` | 5,058 | `Using index` |
| tenant + `user_id = 42` | `idx_audit_logs_identifier_user_id` | 35 | `Using index` |
| tenant + `username = 'user-42'` | `idx_audit_logs_identifier_username` | 35 | `Using index` |
| tenant + `username LIKE '%user-4%'` | `idx_audit_logs_identifier` | 5,058 | `Using where` |
| tenant + `resource_id = 'ins-42'` | `idx_audit_logs_identifier_resource_id` | 14 | `Using index` |

结论：完整 username 等值查询可利用新联合索引，将估算扫描范围从租户级 5,058 降为 35；显式 `fuzzy=1` 的前导 `%` 查询仍扫描租户范围。首次无筛选 Count 也仍随当前租户记录数线性增长，但扫描的是 `identifier` 覆盖索引。

## 剩余风险

1. 首次进入页面的无用户筛选 Count 仍扫描当前租户的 `identifier` 索引范围，成本随租户审计量线性增长；需在预发布观察耗时和 examined rows。
2. 显式 `fuzzy=1` 仍是前导 `%` 查询，会扫描租户范围；调用方应只在确需模糊时使用，操作记录页面主流程仍应选定用户后传 `user_id`。
3. TAPD 最终闭环依赖前端完成「模糊搜索用户候选 → 选中后传 `user_id`」联调；本仓库无法提供前端 MR 证据。
4. `/admin/users?fuzzy=1` 本身是模糊查询，建议小分页并防抖；若后续成为瓶颈，应另立审计主体候选方案。
5. 未执行 K8s/共享环境测试，也未使用生产等量数据验证 P95/P99。
