# 01. Clarify — 需求澄清

## v4 调整（2026-08-05 用户确认）

- `GET /admin/audit?username=<完整用户名>` 改为默认精确匹配，现有 API 调用方无需改变参数名或调用结构。
- 新增 `fuzzy=1` 显式开关；仅在同时传入 username 时使用 `LIKE '%keyword%'`。
- 模糊能力不删除，但从默认高成本路径改为调用方主动选择。
- 前端操作记录页面仍按 `/admin/users?fuzzy=1` 获取候选，选定后发送 audit `user_id`。
- 为默认 username 精确查询新增 `(identifier,username)` 联合索引；现有 user_id/resource_id 联合索引继续保留。
- 用户已明确接受：此前依赖 username 部分字符串且未传 fuzzy 的调用方结果会变为精确匹配。

以下 v3/v2/v1 内容仅保留为历史决策记录；凡与上述 v4 结论冲突之处，均以 v4 为准。

## 轻量方案 v3（2026-08-05 用户确认）

- 撤回独立 `/admin/audit/count`、`include_total=false` 快速列表和进程内缓存。
- `/admin/audit` 继续使用原响应中的同步 `total` / `total_pages`。
- 前端不再把搜索框文本传给 audit 的 `username`；先通过 `/admin/users?fuzzy=1` 模糊查询用户候选，选中后以 `user_id` 精确查询审计记录。
- 后端保留旧 `username LIKE '%keyword%'` 公开 API 语义，仅作为兼容路径。
- TAPD 验收前提：前端调用方式必须同步改变；若仍发送 audit username，原扫描仍可发生。
- 接受首页首次进入时对当前租户执行一次无 username 模糊条件的精确 count；该查询可扫描 identifier 覆盖索引，生产大租户延迟仍需监控。

以下 v2 内容保留为历史决策记录，已由 v3 替代。

## 背景

- TAPD 短 ID：`161733022`；标题：`【clawpro bug 单】/admin/audit 接口全表扫描`。
- 现有 `GET /admin/audit` 在每次列表请求中先同步执行 `COUNT(*)`，计数完成前首页无法展示第一页记录。
- 即使无筛选计数使用 `identifier` 索引，仍需遍历当前租户的全部审计索引记录；用户名前导通配符模糊计数还会扫描租户内候选记录。
- v1 方案新增 `username_exact`，但它要求上游显式切换参数，不符合用户确认的交互方向；本次修订将撤回该参数。
- 前端页面为「操作记录」列表：首页要尽快展示记录，总数允许稍后出现，仍需支持查询和导出所有结果。

## 目标

- [ ] 新前端首屏请求可显式跳过 `COUNT(*)`，列表查询不再被总数统计阻塞。
- [ ] 提供独立的 `GET /admin/audit/count`，使用与列表一致的用户、操作、资源和时间筛选条件。
- [ ] Count 请求按「租户 + 归一化筛选」做有界短 TTL 缓存，并合并同一进程内的相同并发计数，避免重复扫描。
- [ ] 新前端在筛选稳定后防抖请求 count，过期请求结果不能覆盖当前筛选的总数。
- [ ] 用户名输入用于模糊联想用户；选中后按稳定 `user_id` 查询审计记录，不新增精确用户名参数。
- [ ] 保留旧 `username LIKE '%keyword%'` 语义和旧列表默认响应，不破坏 `WithOpenAPI` 公开 API 兼容性。
- [ ] 全量查询/导出能通过分页持续读取直至无后续记录，不依赖预先获取 count。

## 用户已确认的交互

1. 页面先发送不含总数的列表请求，立即展示第一页记录。
2. 总数区域显示「统计中」，前端在筛选稳定后单独请求 `/admin/audit/count`。
3. Count 成功后只更新总数；count 失败不清空或阻塞已展示的列表。
4. 操作人搜索框先模糊查找用户候选，选中具体用户后使用 `user_id` 同时刷新列表和 count。
5. 清空操作人和其他筛选后，恢复全部操作记录和对应总数。

## 默认假设与可验收参数

| 项 | 默认值 | 验收含义 |
|----|--------|----------|
| Count 缓存 TTL | 10 秒 | 相同筛选的总数最多落后约 10 秒，超时后重新统计 |
| Count 缓存容量 | 有界，具体数值在 Plan 确定 | 任意筛选组合不得导致进程内存无限增长 |
| 前端防抖 | 300 ms | 连续输入或切换日期时不对每次变化发起 count |
| 列表兼容 | 旧请求不变 | 未显式选择快速模式时仍返回精确 `total` / `total_pages` |
| Count 错误 | 不影响列表 | 前端可单独重试，不撤销已成功的列表结果 |

## 边界与风险

- **异步的含义**：由前端分别发起列表和 count HTTP 请求；后端 count 接口自身等待数据库结果，不新增轮询任务。
- **缓存一致性**：不引入 Redis 等新外部依赖；多实例的进程内缓存可在 TTL 窗口内返回略有差异的总数。
- **缓存租户隔离**：缓存 key 必须包含请求上下文的租户标识，不得仅使用 URL 参数。
- **过期响应**：前端切换筛选后，旧 count 响应可能晚于新响应；前端需使用请求序号或 `AbortController` 丢弃过期结果。
- **`user_id=0`**：包含 `admin-token` 与多种系统主体，不能视为唯一真人用户；旧 username 查询仍作为特殊主体兼容入口。
- **历史用户**：按 `user_id` 可返回改名前后的记录；已物理删除用户和系统主体不一定能从现有用户联想中找到。
- **筛选计数仍可扫描**：异步 count 与缓存降低首屏等待和重复扫描，但缓存未命中时的精确计数仍需遍历匹配索引记录。
- **前端仓库不在当前工作区**：本轮只能交付 API 与接入说明；前端实装需额外提供对应仓库。

## 历史 v1 结论（已被 v2 替代）
