# 01. Clarify — 需求澄清

> AI 以产品经理角色进行 Discovery + Challenge，确保需求清晰、边界明确。

---

## 背景

Admin 端现有技能、插件、MCP 候选实例查询接口已经能够按资源安装状态筛选，状态参数支持逗号分隔多值；三个下发接口却都要求调用方显式提交 `instance_ids`。这使调用方无法表达“选择全部符合状态的实例”，只能逐页收集 ID。插件和 MCP 的显式 ID 模式还限制单次最多 500 个实例。

本次需求只涉及后端：为三个 `/distribute` 接口增加按安装状态和用户分组解析全部目标实例的能力，不涉及管理前端实现。

## 目标

- [x] `POST /admin/skills/distribute`、`POST /admin/plugins/distribute`、`POST /admin/mcp/distribute` 支持 `select_all=true`。
- [x] 全选模式支持多个资源安装状态和多个用户分组；状态和分组条件均可省略。
- [x] 全选模式在请求受理时生成固定目标快照，不要求调用方提交 `instance_ids`。
- [x] 全选模式不设目标数量上限，并通过分批查询、分批落库和批内 semaphore 控制后端压力。
- [x] 原有显式 `instance_ids` 模式保持参数、数量限制和响应兼容。

### 验收标准

1. `instance_ids` 与 `select_all=true` 严格二选一；无目标模式或同时使用两种模式返回 400。
2. `statuses` 为字符串数组；省略或空数组表示全部允许状态。状态相对于本次下发的目标版本计算。
3. “全部状态”包含 `installed`，但始终排除过渡状态：技能/插件排除 `installing`、`uninstalling`，MCP 排除 `installing`；显式传入过渡状态或非法状态返回 400。
4. `group_ids` 为无符号整数数组；省略或空数组表示不限制分组，多个分组取并集，`0` 表示未分组用户。
5. 目标实例继续执行现有 `/distribute` handler 的 Agent 能力过滤，不新增 `running` 状态限制。
6. 筛选后无目标时返回 400，不创建空任务。
7. 多技能 `skills[]` 模式中，每个技能相对于自己的目标版本独立解析目标实例。
8. 全选模式不设数量上限；目标查询、任务记录和 MCP installation 写入均需分批，每批完成后才读取下一批，并复用现有 `SkillDistributeConcurrency` semaphore，不得按全部目标数创建 goroutine。
9. 单技能、插件、MCP 的全选成功响应返回实际目标数 `total`；多技能响应保留顶层 `total` 的技能项数量语义，并通过各结果的 `instance_count` 返回目标数。
10. MCP 全选响应只返回任务汇总，不展开完整 `per_instance`；显式 ID 模式响应保持不变。

## 范围

| 包含 | 不包含 |
|------|--------|
| 三个 Admin `/distribute` 接口的全选请求契约 | 管理前端或弹窗实现 |
| 资源安装状态多选与全部允许状态 | 实例运行状态筛选 |
| 用户分组多选、`0` 表示未分组 | `search`、`instance_type` 等其他筛选条件 |
| 请求时目标快照与每资源能力过滤 | 持续订阅、实例恢复后自动补发 |
| 不限量目标的分批持久化与批内有界并发 | 修改技能/插件卸载接口 |
| 现有显式 ID 模式向后兼容 | 放宽显式 ID 模式现有数量限制 |

## 约束与依赖

- 三个接口均为已有公共 API，必须保持显式 `instance_ids` 模式向后兼容。
- 写接口继续使用现有 `WithAudit` 包装，不新增路由。
- 数据访问必须使用带请求上下文的 GORM API，保持多租户隔离。
- 异步执行必须使用 detached tenant context。
- 查询、落库和异步执行均按 200 条分批；每批内部使用现有 semaphore 限制活跃 goroutine，完成后再读取下一批。
- semaphore 继续读取现有 `SiteConfig.SkillDistributeConcurrency`，默认值保持 100，不新增外部配置。
- 全选目标是请求时快照；后端不得在执行批次间重新应用状态和分组条件。
- 本次预计不需要数据库 schema 变更。
