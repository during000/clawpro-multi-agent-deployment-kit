# FEC 判定指南（判定权威）

> 本文件是 FEC 象限判定的**单一权威来源**。`skills/feedback/SKILL.md` 与 `rules/feedback-rule.md` 均引用本文件，不重复其内容。

为了防止反馈目录堆满无意义的业务流水账，使用 **FEC 2×2 矩阵** 对用户的每条吐槽/修改意见进行四象限划分。只有高价值信号才允许沉淀为文件。

```
               ▲ 影响范围 (Scope)
               │
               │  【象限 B：隐性知识/规则漏洞】    │  【象限 A：系统性 Skill 逻辑缺陷】
               │  （表面是个案，深层是系统漏洞）   │  （显性的通用问题：格式、字数、幻觉）
               │  - 判定：AI 逻辑没有常理，乱编。 │  - 判定：字数太啰嗦、出现技术词、格式太繁复。
               │  - 动作：通过 RCA 转化为 KB 升级。│  - 动作：直接修改通用 Skill 约束。
全局/系统性 ────┼─────────────────────────────────┼────────────────────────────────────────►
               │                                 │
               │  【象限 D：彻底的无价值噪声】     │  【象限 C：纯业务内容微调】
               │  - 判定：拼写错误、情绪宣泄。     │  - 判定：需求的临时决策变更、纯主观润色。
               │  - 动作：【不生成文件，直接丢弃】│  - 动作：【个案修改，不记入 Skill】
               │                                 │
               └─────────────────────────────────┴────────────────────────────────────────►
                                                      特定需求/个案性 (Particularity)
```

## 🚦 四象限处理动作
- **象限 A (Skill 缺陷)**：**100% 记录**。直接转化为 `SKILL.md` 的全局否定约束（绝对禁止项）。
- **象限 B (知识漏洞)**：**100% 记录**。通过 RCA 根因追溯，补充底座规则，升级 `SKILL.md` 的内置知识库。
- **象限 C (业务微调)**：**不记录**。个案修改直接在单次产物里改掉，不写入 Skill 反馈，避免污染历史。
- **象限 D (垃圾噪声)**：**不记录**。

## ⚠️ 判定时的两个元原则（防漏判 / 防跑偏）

1. **判 A/B 还是 C，看"会不会复发"，不看"用户情绪"。**
   用户平静地提新需求，只要暴露了 AI 默认做法中会在同类生成里复发的系统性缺陷 → 象限 A（记录），不是象限 C。

2. **写行动项前先锁定"真问题/目的"，别把手段当目的。**
   先写用户要解决什么（目的），再写手段，且手段要符合交付物的真实约束（如纯 .md 不能依赖 HTML 渲染）。
