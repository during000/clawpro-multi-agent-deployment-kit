# Update Awareness Skill 使用说明

## 这个 skill 用来做什么

`update-awareness` 用于在 Demo 或产品功能开发完成后，先生成产品经理易读的精简更新提醒方案供人工审核，并在用户明确确认后把可执行提醒植入页面。技术字段保留给 AI 执行，默认不展示；`GuideAdminNotify` 仅做文案生成与审核交接，不由本 skill 决策或开发。

它解决的问题是：新功能上线后，用户需要通过既有引导组件体系知道“哪里变了、为什么变、下一步去哪”，同时按设计规范调用真实组件，而不是在业务页面重新手写浮层或基础视觉。

## 快速使用

最短调用：

```text
使用 update-awareness 生成更新提示方案。
```

推荐补充目标页面和功能修改点：

```text
使用update-awareness，我已经完成管控端 Demo 开发，请识别本次变更并生成更新提示方案，目标页面是xxx。
本次功能修改点：新增插件分发状态筛选，并补充了状态说明列。
```

首次调用默认只生成 `Product Review Plan`，不会修改产品代码，无需额外说明“只生成方案”或“不要修改代码”。审核通过后回复：

```text
确认执行方案 update-awareness-status-filter-2026-07-15 v1。
```

如果方案只包含 `GuideAdminNotify`，skill 只提醒进行文案生成与审核，不会进入代码开发。

Product Review Plan 会为每个可执行组件单独展示 `duration`。默认时长只作为建议，用户必须连同方案一起确认；没有默认值的组件必须先明确天数。方案和 duration 确认、组件实际开发并校验通过后，才会按同一上线批次把 `launched_on`、一个或多个组件、最终文案、挂载位置、代码路径、存在时长和当前用户 ID 登记到目标产品仓库根目录下的 `.clawpro/campaign.yaml`。`launched_on` 默认是登记当天的本地日期；实际发布日期不同时需要明确提供。AI 从该日期开始按各组件的 `duration` 计算下线时间。每次登记成功后还会展示实际写入的 `current_user_id`，必须检查它是否为负责本次组件下线的产品经理。

## 适用场景

当出现以下情况时，可以使用本 skill：

- Demo 功能已经开发完成，需要自动补充更新提醒。
- 产品页面发生结构、入口、按钮、字段、筛选、规则、权限、计费、账号或跨端联动变化。
- 需要判断某个变化是否应该展示更新提示。
- 需要生成中文 `Product Review Plan`，并按需查看完整 `Implementation Plan`。
- 需要把更新提示组件或占位组件挂载到 Demo 页面。
- 需要判断更新提示应使用 onboarding 组件、项目既有组件、设计系统组件还是最小占位适配器。

## 文件组成

```text
项目根目录/
├── .clawpro/
│   └── campaign.yaml
└── update-awareness-skill/
    ├── CHANGELOG.md
    ├── SKILL.md
    ├── 使用说明.md
    ├── agents/
    │   └── openai.yaml
    ├── references/
    │   ├── scenario_rules.md
    │   ├── surface_rules.md
    │   ├── copy_guidelines.md
    │   ├── notification_plan_schema.md
    │   ├── component_contract.md
    │   ├── campaign_schema.md
    │   ├── component_duration_defaults.json
    │   └── onboarding_component_spec.md
    └── scripts/
        ├── create_notification_plan.py
        └── record_campaign.py
```

各文件职责：

- `SKILL.md`：skill 的核心说明，定义触发场景、整体流程、输入、输出和执行要求。
- `.clawpro/campaign.yaml`：位于目标产品仓库根目录的 `.clawpro/` 下，按上线批次记录一个或多个组件，供 AI 计算到期日、提醒产品经理并在确认后创建下线 MR。
- `CHANGELOG.md`：skill 的更新日志，记录规则、脚本、输出结构和接入说明的变化。
- `使用说明.md`：快速说明使用方法和文件组织。
- `agents/openai.yaml`：当前宿主的接入配置，例如展示名称、简介和默认提示词。
- `references/scenario_rules.md`：版本更新场景分类。
- `references/surface_rules.md`：场景到提醒组件的映射规则。
- `references/copy_guidelines.md`：中文文案规范，区分管控端专业文案和用户端易懂文案。
- `references/notification_plan_schema.md`：产品审核方案与技术实现方案的分层结构。
- `references/component_contract.md`：把抽象提醒类型映射到真实引导组件，规定 `component_name`、`type_id` 和接入边界。
- `references/campaign_schema.md`：定义 Campaign 登记字段和写入条件。
- `references/component_duration_defaults.json`：各组件默认存在时长的唯一数据源。
- `references/onboarding_component_spec.md`：完整的引导组件规范汇总，包含真实组件列表、props、层级、定位规则和强制约束。
- `scripts/create_notification_plan.py`：默认生成精简产品审核方案，可选附带完整技术方案。
- `scripts/record_campaign.py`：把实际开发完成的组件安全写入目标产品仓库的 `.clawpro/campaign.yaml`；支持 `--project-root` 和 `--campaign-file`。

## 核心工作流程

1. 识别本次产品变更。
2. 判断目标页面属于 `管控端` 还是 `用户端`。
3. 判断变更属于结构层、元素层、逻辑层、系统层或跨端层。
4. 匹配提醒组件组合，并映射到真实组件，例如 `GuideUpdateBar`、`GuideNavBubble`、`GuidePointBubble`、`GuideHighlightBubble`、`GuideModuleFloat`、`GuideGlobalModal`、`GuideAdminNotify`、`GuideNewTag`、`GuideChangelogDrawer`、`ProductUpdatesDrawer`；完整列表和接入边界以 `references/component_contract.md` 为准。
5. 按端类型读取设计规范，确认基础组件、业务组件和 onboarding 组件的边界。
6. 根据端类型生成中文文案。
7. 默认输出带版本号和等待确认状态的精简 `Product Review Plan`。
8. 停止并等待用户在看到方案后的后续消息中明确确认。
9. 仅按已确认的方案把可执行提醒植入 Demo 或产品页面；`GuideAdminNotify` 与 `GuideUpdateBar` 始终排除在本 skill 的开发范围外。
10. 执行必要校验，确认提醒展示、关闭、过期和挂载位置符合预期。
11. 校验通过后，把同一上线批次的 `launched_on` 和全部实际开发组件登记到目标产品仓库根目录的 `.clawpro/campaign.yaml`；从 `launched_on` 开始计算存在时长，`GuideAdminNotify` 与 `GuideUpdateBar` 不登记。

## 人工确认规则

- 第一次调用永远只出方案，不修改产品代码。即使第一次消息写了“直接做”或“自动植入”，也必须在展示方案后再次确认。
- 推荐回复：`确认执行方案 {plan_id} v{plan_revision}`。
- 修改目标用户、组件、解决问题、展示位置、Trigger、文案、展示策略或视觉素材要求后，方案修订号加一，并重新等待确认。
- selector、import path、props、埋点和持久化等纯技术字段保留在 `Implementation Plan`，默认无需产品经理审核。
- 执行中如果发现方案需要实质变化，停止修改，先给出新版本方案。

特别规则：

- 每一项用户端变化都独立判断管理员是否需要管理或知情，不限于跨端层、入口或 New Tag。
- 变化影响配置、治理、安全、数据访问、支持、解释或故障排查时，识别一项 `GuideAdminNotify` 告知需求，提醒用户先进行卡片文案生成与审核；本 skill 不直接开发，也不决策该组件开发。
- 管控端需要 Banner/公告条时，识别一项 `GuideUpdateBar` 需求，提醒用户先进行公告文案生成与审核；本 skill 不直接开发，也不决策该组件开发。
- 纯交接方案状态为 `handoff_required`，不生成生命周期、持久化、埋点、设计接入或目标文件；混合方案只为其他可执行组件生成这些字段。
- 执行前必须硬过滤 `GuideAdminNotify`、`GuideUpdateBar` 及其各自关联详情条目。过滤后没有可执行组件时立即停止，不修改产品代码。
- 用户端支持云端 Agent 对话、模型调用、工具调用或外部连接等重要能力时，即使没有直接配置入口，也需要告知管理员。
- 如果只是新增下载 skill 的地方、帮助页、展示页或纯浏览入口，不需要在管控端提示。

多场景规则：不同目标用户、认知问题、页面或 Trigger 需要分别提示；只有同一用户、同一问题、同一位置且同时触发时才合并。场景优先级只决定顺序，不删除其他必要提示。

双端卡片的简化判断：

- 用户要知道的新能力，用用户端卡片。
- 管理员必须知道、否则会影响管理或解释口径的用户端变化，用管控端卡片。
- 纯下载、帮助、展示、浏览类入口，两边通常都不用卡片。

组件映射时还要注意：

- 先判断用户会因为什么出错，再选组件，不要先看到组件名再反推场景。
- 同一认知问题默认只保留一个主组件和一个定位组件，不要堆三层重复提示。
- `New Tag` 只负责标新，不负责解释规则、权限、计费或逻辑变化。
- 管控端日常更新提示可识别为 `GuideAdminNotify` 需求，但只做文案生成与审核交接，不进入本 skill 的开发决策。用户端 `GuideModuleFloat` 是跨页面全局产品动态浮窗，固定含 16:9 配图区，只用于高/重大、必须跨页面触达且轻量提示不足的更新；一旦命中，必须提醒用户联系设计团队进行图片设计。
- 管控端导航提示条可识别为 `GuideUpdateBar` 需求，但只做公告文案生成与审核交接，不进入本 skill 的开发决策或执行范围。
- `GuideAdminNotify` 固定展示在管控端，但卡片 `endpoint` 表示内容所属端；用户端变化告知管理员时使用 `endpoint="tenant"`。
- 多个用户端浮窗通知单元保留各自问题和 Trigger，但渲染时通过一个 `GuideModuleFloat` 的 `sources` 分页合并。
- `GuideModuleFloat` 挂在登录后的用户端全局布局，在任一允许页面均可展示；路由切换不重复曝光，并排除登录页、首次 onboarding、全屏/沉浸任务和 GlobalModal 打开期间。
- 用户端抽象命中“导航提示条”或页面入口气泡时，优先改用 `GuidePointBubble`、`GuideNewTag` 或不展示；`GuideNavBubble` 仅用于管控端，不得自动升级为 `GuideModuleFloat`。
- `ProductUpdatesDrawer` 只做管控端产品动态详情承接，不作为单步引导气泡使用。
- `GuidePointBubble` 选纯文本时显式传 `contentVariant="text-only"`；`GuideNewTag` 没有 `open/onClose`，`GuideUpdateBar` 没有 `onClose`。
- `GuideOnboardingModal`、`OnboardingSimToggle` 和 `OnboardingDemoPanel` 不用于生产版本更新提示。
- 所有 onboarding 正式导入固定使用 `@/components/onboarding`，不从参考源码目录或具体组件文件深链导入。
- 使用 `GuideModuleFloat` 时，产品审核方案必须主动提醒“请联系设计团队进行图片设计”，并写明素材规格和上线前置条件；`GuideGlobalModal` 或其他带图变体也须标注设计素材要求。组件源码占位图不得用于生产。

文案和生命周期要符合组件定义：

- 普通 onboarding 文案：标题不超过 14 字，正文不超过 60 字，CTA 不超过 6 字。
- `GuideAdminNotify` 卡片：仅把标题、正文和按钮长度作为文案 brief，分别为标题不超过 16 字（含 `管控端 |` 或 `用户端 |` 前缀）、正文不超过 30 字、按钮不超过 6 字；最终文案需另行生成与审核。
- `GuideNewTag` 默认 `variant="new"` 显示 `New`；建议 14 天下线，最长 30 天，也可以首次点击后移除。
- 持久化 key 使用 `onboarding.{component}.{update_id-or-unit-id}.dismissed` 这类格式，并保证每个通知单元独立；埋点使用 `onboarding_impression`、`onboarding_click`、`onboarding_dismiss`。

## 需要提供什么信息

建议提供：

- 产品或 Demo 名称
- 端类型：`管控端` 或 `用户端`
- 目标页面、路由、组件路径
- 本次开发完成的功能说明
- 影响用户：`管理员` 或 `普通用户`；运营、审核、配置等后台角色归入管理员
- 变更文件、PR 摘要、提交差异或页面代码
- 版本号、发布日期、灰度条件、功能开关
- 是否已有 `@/components/onboarding`
- 是否已有管控端 / 用户端设计规范或基础组件导出
- 当前用户 ID；建议显式提供能接收下线提醒的产品经理 ID。不提供时，登记脚本只会回退到本机操作系统用户名（例如本机登录账号），它不一定等同于产品经理平台账号，写入后必须检查
- 上线日期；默认使用方案确认、组件植入并通过校验后登记 Campaign 的当天日期，实际发布日期不同时需明确提供
- 每个组件的存在时长；不提供时分别使用该组件的默认值并提醒检查

如果信息不完整，skill 会根据路由、页面名、组件名、文案和代码结构做推断，并在计划里标注假设。

## Agent 接入

在其他 Agent 中使用时，先读取：

```text
update-awareness-skill/SKILL.md
```

然后按 `SKILL.md` 的当前阶段按需读取引用文件，不要在首次调用时无条件加载全部资料：

- 识别场景和选择组件时，读取 `scenario_rules.md`、`surface_rules.md`、`component_contract.md` 和对应的 `onboarding_component_spec.md`。
- 生成文案和审核方案时，读取 `copy_guidelines.md` 与 `notification_plan_schema.md`。
- 实际登记 Campaign 时，读取 `campaign_schema.md` 与 `component_duration_defaults.json`。
- 只有工作区确实存在 `clawpro-portable-design-skill/` 时，才按管控端或用户端读取其对应规范；不存在时使用项目已有设计系统和本 skill 的组件契约。

## 输出内容

标准输出是一个产品经理可快速审核的中文 `Product Review Plan`，只包含：

- 更新内容和目标用户
- 选择的组件及其解决的问题
- 挂载页面、目标元素、相对方位和 Trigger
- 与组件真实内容槽位匹配的文案；无按钮的组件不补按钮
- 展示次数和关闭方式
- 每个可执行组件的 duration 建议或待确认天数
- 方案版本、状态和确认语句

`type_id`、selector、import path、props、持久化、埋点、注入策略和技术占位符保留在内部 `Implementation Plan`。用户明确要求查看完整技术方案时，脚本可使用 `--include-implementation` 输出。

## 真实组件和占位

优先顺序：

1. 直接复用 `@/components/onboarding`
2. 对 Alert、字段说明、原名标注、按钮、卡片、表格、空态等基础能力，复用项目既有组件或设计系统组件
3. 只在必要时创建最小占位适配器，并写明后续替换目标

禁止在业务页面重新手写一套引导浮层，也禁止用 `div + className` 临时拼出设计规范中已有的组件视觉。
