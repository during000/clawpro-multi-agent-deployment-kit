# 提醒组件映射规则

版本更新通常使用“组件组合”，不要只选一个组件。除非场景明确“不展示”，否则至少输出一个主组件和一个挂载位置。

组件的真实 React 组件名、`type_id` 和接入边界以 `component_contract.md` 为准；完整组件说明见 `onboarding_component_spec.md`。本文件只负责“场景应该匹配哪些组件”。

## 组件定义

## 选型总原则

先判断“用户会因为什么出错”，再选组件，不要先看到组件名再反推场景：

1. 用户不知道有这个能力或入口：优先 `导航提示条`、`日常更新提示`、`New Tag`
2. 用户知道有变化，但找不到具体入口或新位置：优先 `页面入口气泡引导`、`功能入口附近气泡`
3. 用户知道位置，但不理解规则或结果为什么变了：优先 `页面 Alert`、`对应组件下方规则说明`
4. 用户旧路径会直接失败、权限会被拒绝、结果会与旧逻辑不一致：至少使用 `导航提示条` 或 `页面 Alert`
5. 只有重大知情确认场景，才升级到 `强提醒弹窗`

默认选“能解决问题的最低打扰度组件”，但不能为了降打扰度而丢失必要信息。

## 多场景处理

一次更新可以命中多个场景，也可以产生多个提示。不要只保留优先级最高的场景。

1. 先把每个场景转成独立认知问题。
2. 按目标用户、认知问题、页面/目标元素和 Trigger 分组为通知单元。
3. 不同目标用户、不同问题、不同页面或不同触发时机，分别生成提示项。
4. 同一用户、同一问题、同一位置且同时触发的场景可以合并，避免重复打扰。
5. 优先级只决定先展示哪个、哪些需要排队或避让，不等于只展示一个。

例如同一版本同时“新增页面”和“修改计费规则”时，新增页面可使用入口提示，计费规则必须在计费页使用 Alert；两者不能因为系统/逻辑层优先级更高就删除入口提示。

### 导航提示条

用于跨页面、入口级、规则级或需要管理员普遍知晓的更新。

默认实现：

- 管控端优先识别为 `GuideUpdateBar` 需求，但本 skill 只发起公告文案审核与开发决策交接，不负责开发或植入
- 用户端优先 `GuidePointBubble`、`GuideNewTag` 或不展示；`GuideNavBubble` 仅用于管控端
- 只有高影响且必须跨页面触达时，用户端才升级为 `GuideModuleFloat`

适用：

- 新页面、新入口、入口下线
- 页面结构变化
- 底层逻辑、规则、计费、权限、合规变化
- 已知问题修复需要告知

默认位置：

- 页面顶部
- 管控端首页顶部
- 对应模块导航区域下方

### New Tag

用于入口、Tab、按钮等轻量“新功能”标识。

默认实现：

- `GuideNewTag`

适用：

- 新增子页面
- 非一级导航新增入口
- 新增 Tab 或功能入口

默认策略：

- 展示 14 天或直到用户首次点击。
- 最长不超过 30 天。
- 必须在计划里写明下线条件。
- New Tag 仍需执行管理员知情判断，但该判断对所有用户端变化都执行。涉及管理、治理、安全、支持、解释或排查时，识别一项管控端 `GuideAdminNotify` 告知需求并转交文案生成与审核；纯下载、浏览、帮助或静态展示入口通常只保留用户端 New Tag。

### 气泡引导

用于指向具体入口或元素，解释新位置、新操作或新含义。

细分及默认真实组件：

- `页面入口气泡引导`：指向侧边栏、导航、Tab、页面入口，默认 `GuideNavBubble`
- `重要操作变更气泡引导`：指向页面重排后的关键操作区，默认 `GuideHighlightBubble`
- `功能入口附近气泡`：指向按钮、筛选、表格列、字段等，默认 `GuidePointBubble`
- `禁用入口说明气泡`：指向预下线或暂时禁用入口，按目标位置选择 `GuideNavBubble` 或 `GuidePointBubble`

默认策略：

- 首次进入目标页面展示。
- 用户关闭、点击目标入口或曝光 2 次后不再展示。
- 如果目标元素属于同页重复组件，默认只给首个实例展示一次指引。

### 侧边栏说明详情

用于页面拆分、复杂结构重组、跨模块入口解释。

默认实现：

- 优先 `GuideChangelogDrawer`
- 如果产品已存在等价右抽屉或侧边栏说明容器，优先复用

适用：

- 一个页面拆分为多个
- 多个入口对应不同任务，用户需要理解差异

### 页面 Alert

用于页面内解释规则、逻辑、计费、配额、权限、合规或已知问题修复。

默认实现：

- 优先复用项目已有 Alert
- 不要为了“看起来像提醒”而拿 onboarding 气泡硬代替 Alert

适用：

- 底层逻辑变更
- 规则、策略、计费、配额变更
- 权限、账号、合规变化
- 已知问题修复

默认位置：

- 对应页面主内容顶部
- 对应表单或配置区上方

### 常驻操作引导

用于操作路径大幅调整，且用户在短期内需要反复参考。

默认实现：

- 优先 `GuideHighlightBubble`

适用：

- 细节优化叠加但实际改变了操作路径
- 页面重排后关键任务路径变复杂

### 对应组件下方规则说明

用于普通输入规则变化，不需要全局提醒。

适用：

- 表单校验说明
- 命名规则
- 字段输入限制

### 强提醒弹窗

仅用于最高风险变化。

默认实现：

- 使用 `GuideGlobalModal`

适用：

- 账号体系变化
- 数据合规或隐私政策变化
- 需要用户确认知情或同意的变化

### 日常更新提示

用于需要明确感知的更新汇总。管控端卡片可承载日常产品动态；用户端 `GuideModuleFloat` 视觉较重，不作为普通日常更新的默认提示。

默认实现：

- 管控端优先 `GuideAdminNotify`
- 用户端仅在影响等级为高/重大、需要跨页面触达且轻量组件不足时使用 `GuideModuleFloat`
- 用户端低/中影响更新优先局部气泡、New Tag 或不展示

流程边界：命中 `GuideAdminNotify` 只代表需要管控端产品动态告知。本 skill 必须提醒用户进行卡片文案生成与审核，不直接开发，也不决策该组件是否进入开发。命中 `GuideModuleFloat` 时必须提醒用户联系设计团队进行图片设计，素材审核通过前不可执行植入。

跨端要求：

- 对每项用户端变化单独执行管理员知情判断，不限于跨端层、页面入口或 New Tag 场景。
- 用户端变化影响配置、下发、权限、治理、安全、数据访问、统计、支持、解释或故障排查时，识别一项管控端 `GuideAdminNotify` 卡片需求，并转交文案生成与审核流程。
- 用户端新增重要能力，即使没有直接的管控端配置动作，只要管理员需要知道用户能做什么以及如何支持、治理或解释，也应通知管理员。例如用户使用云端 Agent 对话、模型调用、工具调用或外部连接。
- 卡片标题建议以 `用户端 |` 开头，描述用户侧新增能力及管理员需要知道的管理或知情影响。
- CTA 优先打开 `ProductUpdatesDrawer`，并用 `relatedIds` 高亮对应产品动态条目。
- 用户端只是新增下载 skill 的地方、帮助页、展示页或纯浏览入口时，不生成管控端卡片。

### 组合覆盖规则

多个组件同时命中时，按下面规则收敛，避免同一页面堆过多提示：

1. `导航提示条` 负责告诉用户“发生了什么”，气泡负责告诉用户“具体在哪”；命中 `GuideUpdateBar` 时前者作为交接项，不进入本 skill 的可执行集合
2. `页面 Alert` 负责解释规则或结果变化，不再额外用 `GuidePointBubble` 重复解释同一段规则
3. `New Tag` 只负责轻量标新，不负责解释规则、迁移路径或影响范围
4. `GuideModuleFloat` / `GuideAdminNotify` 负责日常汇总提醒，不替代页面内的定位气泡
5. `GuideHighlightBubble` 只在多步骤迁移、路径重排、连续操作引导时使用；单一元素说明退回 `GuidePointBubble`
6. 同一认知问题最多保留一个主组件和一个定位组件；不要同时放 `UpdateBar + ModuleFloat + PointBubble` 去表达完全同一件事
7. 多个独立通知单元仍分别保留；只有多个用户端 `GuideModuleFloat` 在同屏冲突时，才用一个实例的 `sources` 把各通知单元分成多页。该合并不改变各自的问题、Trigger 和持久化记录。
8. `GuideModuleFloat` 固定含配图区；一旦选择，Product Review Plan 必须主动提醒用户联系设计团队进行图片设计，并写明素材上线前置条件。
9. `GuideAdminNotify` 只输出需求识别与文案生成/审核交接，不进入本 skill 的开发执行范围。

### 禁止映射

这些情况默认不允许：

- 用 `New Tag` 解释规则变化、权限变化、计费变化
- 用 `GuidePointBubble` 代替页面级规则说明或 Alert
- 用 `GuideAdminNotify` 代替用户端提示，或反过来用 `GuideModuleFloat` 代替管控端产品动态卡片
- 用户端只是新增下载、帮助、浏览、展示入口，却强行映射为 `GuideAdminNotify`
- 同一个新增入口既挂 `New Tag`，又挂 `GuidePointBubble`，又挂 `GuideModuleFloat`，但三者都在重复说“这里新增了”
- 低/中影响用户端更新仅因“需要跨页面展示”就使用 `GuideModuleFloat`
- 用 `GuideModuleFloat` 或 `GuideGlobalModal` 的源码占位画面替代正式设计素材

## 双端卡片判定表

| 更新类型 | 用户端卡片 | 管控端卡片 | 说明 |
| --- | --- | --- | --- |
| 用户端新增页面、入口、操作，且用户不容易主动发现 | `GuideModuleFloat` 或用户端其他更新提示 | 独立判断 | 普通用户需要知道入口；管理员是否需要知情取决于管理、治理、支持和解释影响 |
| 用户端新增页面，但本质只是下载、浏览、帮助、教程、静态展示 | 否或仅 `New Tag` | 否 | 不改变管理员管理对象，也不需要额外打扰用户 |
| 用户端新增需要管理员管理或知情的能力，例如 skill 下发更新、云端 Agent 对话、模型/工具调用、启停状态、分发结果 | 视用户是否需要主动感知，可用 `GuideModuleFloat` / `New Tag` | 是，`GuideAdminNotify + ProductUpdatesDrawer` | 不要求存在直接管控配置，只要管理员需要治理、支持、解释或排查即可 |
| 管控端配置保存后会直接改变用户端入口、默认内容或能力范围 | 是，用户端优先 `GuideModuleFloat` 或页面内提示 | 视情况而定 | 核心是让用户知道“这是管理员配置后生效的” |
| 纯视觉优化、轻微流畅性优化、不改路径不改结果 | 否 | 否 | 走 `不展示` |

执行顺序：

1. 先判断变化是否值得主动提示。
2. 再独立判断普通用户是否需要提示、管理员是否需要管理或知情。
3. 如果同时影响两边，各自使用对应端的卡片，不要拿一种卡片代替另一种。

## 主组件决策表

| 首要认知问题 | 主组件优先级 | 备注 |
| --- | --- | --- |
| 不知道新增了页面或入口 | `导航提示条` / `GuideModuleFloat` / `New Tag` | 是否跨页面、是否需要持续可见，决定三者谁做主 |
| 不知道新入口具体在哪 | `页面入口气泡引导` | 入口在导航、Tab、侧边栏时优先 |
| 不知道按钮、筛选、字段具体在哪 | `功能入口附近气泡` | 单点说明默认它 |
| 不理解页面为什么和原来不一样 | `重要操作变更气泡引导` | 页面重排、迁移路径、多步骤任务 |
| 不理解规则、权限、计费、结果为何变化 | `页面 Alert` | 页面级规则变更优先，不要退化成小气泡 |
| 需要管理员知道用户端新增能力 | `GuideAdminNotify` | 有管理、治理、支持、解释或排查影响时成立 |
| 只是轻量标新 | `New Tag` | 不承担完整解释职责 |

## 端类型映射补充

同一个抽象场景在不同端的默认主组件不同：

| 抽象场景 | 用户端默认主组件 | 管控端默认主组件 |
| --- | --- | --- |
| 日常更新提示 | 低/中影响用局部气泡/New Tag/不展示；高影响跨页面更新才用 `GuideModuleFloat` | `GuideAdminNotify` |
| 入口级强提醒 | `GuideNavBubble` 或 `GuidePointBubble`；高影响跨页面触达才用 `GuideModuleFloat` | `GuideUpdateBar` 或 `GuideNavBubble` |
| 页面级规则变化 | 页面内提示 / Alert | `GuideUpdateBar + 页面 Alert` |
| 跨端联动变化 | 用户端按影响决定是否提示 | 管控端优先 `GuideAdminNotify` |

### 不展示

用于不值得打扰用户的变更。

适用：

- 纯视觉优化
- 仅让已有操作更顺畅
- 不改变路径、不改变结果、不影响理解的细节调整

## 打扰度判断

高打扰度：

- 强提醒弹窗
- 页面 Alert
- 常驻操作引导

中打扰度：

- 导航提示条
- 侧边栏说明详情
- 气泡引导
- 日常更新提示

低打扰度：

- New Tag
- 新名称右侧标注原名称
- 组件下方规则说明

默认选择能解决认知问题的最低打扰度组合。若旧路径会失败、权限会变化、规则会拒绝用户操作，则必须使用导航提示条、页面 Alert 或强提醒弹窗。

`导航提示条` 命中 `GuideUpdateBar` 时仍保留在产品审核方案中，但必须标记 `handoff_required`。本 skill 不生成可开发终稿，不开发、植入、修改或登记 `GuideUpdateBar` 及其关联详情条目。
