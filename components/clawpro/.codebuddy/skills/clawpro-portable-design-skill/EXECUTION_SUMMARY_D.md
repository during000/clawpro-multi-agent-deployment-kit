## ✅ D1 - 补充"冲突由设计师裁决"的铁律

### 新增位置
- **文件**: `SKILL.md`
- **位置**: §1 Principles 后新增 §1.5
- **行数**: ~54 行（从第 109 行开始）

### 内容要点

#### 核心原则（§1.5 开头）
> 当 Spec 与代码现状冲突、或 Token / Variant / 圆角 / 图标槽位等设计拍板模糊时，
> **必须停下来回到设计师**，而不由 AI 或工程师私自裁决。

#### 冲突的三个来源
1. **规范与现实冲突** — Spec A vs 现状 B
   - 例：Spec 4px，现状 8px
   - 处理：标 `needs-design-confirmation`，交设计师选择
   
2. **业务需求与规范冲突** — 产品超范围需求
   - 例：新增未定义的状态
   - 处理：先补规范再落地
   
3. **设计选择模糊** — 两个选项都可行但有隐藏成本
   - 例：圆形渐变 vs 方形扁平图标
   - 处理：列出成本对比，交设计师定夺

#### 冲突记录流程（4 步）
1. 遇到冲突 → 在 `references/conflict-log.md` 记录（位置、冲突方 A/B、成本分析）
2. 设计师 review → 补充裁决原因和避免办法
3. 根据裁决执行改动 → 标注 `Ref: conflict-log.md #N`
4. 同步更新规范 → 防止再犯

#### 不允许 / 允许的做法清单
**不允许**：
- 为快速交付私自裁决
- 对图标槽位直接选 lucide（应标 needs-design-confirmation）
- 看到不一致就"为了兼容"忽视 Spec
- 自行扩展规范（应先补规范）
- 累积冲突到下个月再处理

**允许**：
- 冲突时立刻标记，交设计师处理
- 图标无候选时用临时占位符，等设计确认
- 新需求超范围时先补规范再实现

### 新增 7 个小节

#### 12.1 冲突定义
明确界定冲突的 4 种情况：
- Spec 与实现不一致
- 需求超出规范范围
- Token / Variant / 图标槽位 / 圆角 / 阴影 设计拍板模糊
- 宿主仓现状与 Spec 差异

#### 12.2 冲突处理流程（4 步）
1. **识别冲突** — 遇到时立刻停下来
2. **记录冲突** — 位置、格式、同步记录（不积累）
3. **交设计师裁决** — 下一个 design review 周期统一处理
4. **执行改动** — 按裁决执行、标注 Ref、更新规范

#### 12.3 不同类型冲突的处理方式（表格）
| 冲突类型 | 示例 | 处理方式 | 时间框 |
|--------|------|--------|--------|
| Spec vs 现状 | Spec 4px，现状 8px | 标记冲突，交设计师选择 | 下一个 design review |
| 需求超范围 | 新增未定义状态 | 先补规范，再落地 | 前置 1-2 天 |
| 图标无候选 | 业务图标无合适 SVG | 标 needs-design-confirmation，用临时占位 | 后续由设计提供 |
| Token 模糊 | 不确定用什么 token | 列 2-3 方案，交设计选 | 下一个 design review |
| 宿主仓兼容 | 宿主仓与我们差异 | 列差异，交设计拍板 | 需要产品+设计对齐 |

#### 12.4 铁律（核心约束）
**一句话**: 冲突没有设计师裁决就不动手。

具体禁止事项：
- 为快速交付私自裁决
- 对图标槽位直接选 lucide
- 为了兼容忽视 Spec
- 自行扩展规范
- 累积冲突

#### 12.5 图标槽位特殊规则
- 基于 §2.8 的图标决策流程单独处理
- 无合适候选时的标准做法：检查 → 查询 → 无合适时标 `needs-design-confirmation`
- 不允许直接降级 lucide、手搓 inline SVG、自定义颜色

#### 12.6 冲突日志审查
- 设计师每周 review 一次 conflict-log.md
- 积压超过 3 个冲突未处理 → 立刻升级
- 定期复盘根因，改进规范或流程

#### 12.7 冲突的信息出口
冲突记录 + 裁决 = 知识库：
- 新成员理解设计决策背景
- 发现规律性冲突时补规范
- 定期生成"设计决策史"文档

## 🎯 成果总结

### 团队纪律固化
Phase D 通过 §1.5 + §12 两个部分，将 A/B/C 各阶段的所有"铁律"和"禁止事项"制度化为：

**冲突处理的标准流程**：
1. 识别冲突（AI / 工程师）
2. 记录冲突（`references/conflict-log.md`）
3. 设计师裁决（design review 周期）
4. 执行改动（带 Ref 标注）
5. 规范同步（防止再犯）

**四类冲突的标准处理方式**：
- Spec vs 现状 → 选择权交设计师
- 需求超范围 → 先补规范再实现
- 图标无候选 → 标 needs-design-confirmation
- Token 模糊 → 列选项交设计师

### 关键保护机制

1. **禁止私自裁决** — 所有"看起来好"的选择都可能有隐藏成本，必须设计师介入
2. **图标槽位零退步** — 不允许从 registry SVG 降级回 lucide，标 `needs-design-confirmation` 等设计补绘
3. **规范同步循环** — 每个冲突 → 设计师裁决 → 规范补充，建立知识库
4. **周期审查** — 设计师周周 review conflict-log.md，防止冲突积压
