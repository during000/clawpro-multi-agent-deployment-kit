# ClawPro 协作守门（轻量版）

本规则在 ClawPro 工作空间内自动生效。用户只需描述需求，不必选择分支、复制开发 Prompt，或额外说“按协作规范”。

- 人工职责索引：`.codebuddy/docs/clawpro-branch-ownership.tsv`
- 工蜂实时索引：每个独立新需求由 `.codebuddy/scripts/sync-clawpro-branches.py` 生成到 Git 内部目录，不提交进仓库
- 完整人工手册：`.codebuddy/docs/ClawPro多人协作分支开发规范.md`
- 普通任务只用本规则和快速索引；仅在首次配置、异常处理、MR 模板或规则争议时读取完整手册。

## 1. 新需求先路由，同一开发上下文复用确认

1. 用 `git rev-parse --show-toplevel` 定位当前 clone 的仓库根目录，确认 `origin` 属于 `cvm-openclaw/openclaw-enterprise`；不要扫描或修改仓库外的兄弟目录。
2. 每个独立新需求先从仓库根目录执行一次且只执行一次 `python3 .codebuddy/scripts/sync-clawpro-branches.py --origin origin`。该脚本通过 `git ls-remote --heads origin` 同步全部工蜂 `feature/*`，并输出 `LIVE_TSV=<path>`；实时 TSV 写入 Git 内部目录，不造成工作区修改。同一需求的补充调整、修复、验证、预览、提交、推送或 MR 不算独立新需求。
3. 从需求提取端侧、页面、Tab、模块和功能关键词，使用 `rg -ni '<关键词>' '<LIVE_TSV 输出路径>'` 匹配职责；仅在不能唯一匹配时只读搜索代码。`registered + active` 可用于正常路由；`missing` 不得创建同名分支；`unregistered` 只作为候选并提示职责待确认。
4. 优先选择已经检出目标分支的仓库，先执行 `git status --porcelain=v1` 和 `git fetch origin --prune`。只有需要切换分支时才要求工作区干净；必要时安全切换到远端 tracking 分支。本阶段不 rebase、不改文件。
5. 首次进入目标仓库时，将现有 `git status --porcelain=v1` 记录为本对话的“未提交修改基线”，只说明一次并保护这些内容。当前分支已经是目标分支时，基线不为空不代表异常，也不阻止确认或继续；不得自动 stash、reset、覆盖或删除。只有需要 switch/rebase、发现基线之外且不属于本次计划的新文件、既有修改与本次修改发生无法安全区分的重叠，或工作区被外部切换时才停止。实时 TSV 位于 Git 内部目录，不计为工作区修改。多候选、远端不存在、职责冲突或分支被其他 worktree 占用时也停止，请用户选择。
6. 没有已确认上下文，或匹配结果将切换仓库、分支或职责模块时，回复必须以以下连续三行收尾，然后停止：

   ```text
   【分支匹配待确认】
   分支：feature/xxx
   请确认是否在该分支继续。
   ```

   实际回复不要使用代码块。CodeBuddy 自动展示的定位和工具过程不算规则失败。
7. 用户明确回复“确认”“继续”“可以”等同意语义后才能首次写代码。确认在当前 CodeBuddy 对话、仓库和分支内持续有效；同一页面或职责范围内的补充修改直接继续，不重复展示确认区块。只有需求明显转到其他仓库、分支或职责模块，实际分支被外部切换，或输出了新的分支确认区块时，才重新确认。
8. Hook 拒绝时按原因纠正，禁止绕过；Hook 未加载时请用户在 `/hooks` 启用“ClawPro 分支确认与单仓写入门禁”。

## 2. 确认后：安全开工

1. 首次确认后再次执行 `git fetch origin --prune`，并记录未提交修改基线及本次计划文件。后续连续任务中的本次改动属于正常开发状态，不重复提示“工作区有未提交修改”；只有基线外的未知改动或覆盖风险才提示。
2. 禁止在 `main` 开发。首次写入前，工作区干净时同步当前 `origin/<feature>` 并 rebase 最新 `origin/main`；已有基线修改时，先确认当前 HEAD 已包含最新 `origin/main` 且远端 feature 未领先或分叉，满足时保留修改继续，不满足时只阻止需要 switch/rebase 的操作并说明一次，禁止自动 stash。连续开发中不因本次任务产生的 dirty worktree 重复执行 rebase 或停止。
3. rebase 冲突时停止，逐文件说明双方意图；禁止批量选择 ours/theirs。
4. 开始修改前列出本次计划文件，只操作已确认仓库。

## 3. 范围与实现

- 默认只改当前分支负责的页面。未经 `qitinghuang` 明确授权，禁止修改 `App.tsx`、`AdminLayout.tsx`、导航、公共路由，禁止新增子页面、子 Tab 或顺手修改其他分支。
- UI 改动读取当前仓库已有的 ClawPro 设计 Rule、Skill、组件规范和 Token；不自创颜色、圆角、字号、间距、阴影，不用 emoji 或手写 SVG 代替图标库。缺失规范标记 `needs-design-confirmation`。
- 基础信息配置、用户管理、Agent 列表、Tokens 监控默认检查普通、OneID 专用、统一三种账号模式。
- 不做无关格式化，不静默修改锁文件，不提交 SSH 私钥、Token、Cookie、密码或生产凭据。
- 发现跨分支依赖立即停止越界修改；代码恢复使用 Git 提交、`reflog`、备份分支或补丁，不依赖 AI 对话记录。

## 4. 完成与预览

交付前按改动范围执行：

1. 检查 `git diff`、受保护文件和范围边界。
2. 从当前 `package.json` 读取真实脚本，执行适用的类型检查、测试和构建；不得虚构命令。缺少 Node、pnpm、测试浏览器或其他运行时环境时，先说明安装位置和影响并征得用户确认；不得自行安装全局工具或修改用户环境。
3. 验证主路径及本次涉及的空、加载、错误状态和账号模式；UI 改动执行设计自查。
4. UI 改动启动或复用本地服务，从终端取得实际端口，验证目标路由可访问并返回可点击直达链接。不得写死端口或只给首页。失败时给出原因和复现命令。
5. 最终回复前重新执行 `git status --short`，一次性区分“开始前已有基线修改”和“本次任务修改”。用户说“只做本地修改”仅表示不提交、不推送、不创建 MR，不表示跳过检查或预览；只有明确说“不启动预览”才跳过。

最终回复只保留：

```text
已完成：<改动>
分支：<feature/*>
验证：<实际检查和结果>
预览：<目标页面链接；非 UI 写不适用；失败写原因和命令>
工作区：<最新未提交文件数和本次文件>
提交状态：<未/已提交>、<未/已推送>、<未创建 MR/MR 链接>
```

存在本地修改时不得写“工作区干净”。

## 5. 提交、推送和 MR

只有用户明确说“提交”“推送”或“提 MR”才执行：

1. `git fetch origin --prune`，安全同步当前 feature 并 rebase 最新 `origin/main`；冲突即停止。
2. 复跑必要检查，确认 Source 为当前 `feature/*`、Target 为 `main`。必需检查失败时，区分本次引入与分支既有问题并停止；只有向用户说明失败项且获得“仍然推送”的明确确认后才能继续。
3. 提交和推送当前分支；MR 描述包含背景、范围、验证、预览或截图、风险、回滚和待确认项。
4. 已安装且已认证工蜂 API/CLI 时创建 MR；能力不可用时不得声称已创建，只返回预填创建链接并写明“MR 未创建，等待人工打开链接确认”。不得为创建 MR 自行安装 CLI 或索取、输出访问 Token。
5. 禁止 `force`。只有确认远端分支无人共用且获得用户确认后才可 `force-with-lease`。

## 6. 只读自测

用户说“测试协作规范，不改代码”时，只读检查仓库、分支、origin、工作区和受保护范围，不 fetch、不 rebase、不写文件；最后输出：

`【自测通过】以后只需直接描述需求。`
