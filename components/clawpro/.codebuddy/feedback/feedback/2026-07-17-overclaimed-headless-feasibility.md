- **系统性缺陷根因**：
  - [x] **信息缺失未留白**：输入未提及该参数，AI 开启了"自动填充数值"的默认幻觉。
  - [x] **底座知识断层**：AI 不知道平台底座的真实生命周期/限制。
  - [ ] **角色定位偏移**：思维没立足于"资深 PM 跨所有者全局运维"视角，降级为普通助理。
  - [ ] **模板固化**：模板过于死板，无法按需求复杂度动态裁剪模块。

## 追加记录（2026-07-20）
- **补充原话**：
  > "Stop指的是啥？和 SessionEnd 的区别是啥？Stop是每一个回复的结束吗？"
- **补充 RCA**：上一轮实施与 SKILL.md 文案把 Stop hook 描述为"会话结束统一收口"，但官方文档明确 Stop 是"主 agent 每完成一次响应（每一轮回复结束）"时触发的回合级事件、一个会话可多次触发；真正会话级只触发一次的是 SessionEnd，而 SessionEnd 又不能 block 把 AI 拉回判定。因对 hook 触发粒度（回合级 vs 会话级）理解断层，进一步设计出错误的 cursor 游标：游标按"skill 调用条数"推进，会在"产物刚生成、尚无用户反馈"的当轮就被 Stop 触发并过早推进，导致用户在后续轮次给出的真实反馈因无新增调用而不再触发拉回，被漏记
- **补充优化项**：
  - 目的=正确理解并使用平台 hook 的触发粒度，避免基于错误语义设计自动化；手段=设计任何 hook 方案前先逐个核实每个事件的"触发粒度/频率"与"能力边界"——Stop=每轮回复结束(回合级/可多次/能 block 拉回)、SessionEnd=整会话仅一次(会话级/不能拉回)、PostToolUse=每次工具后；严禁凭事件名的字面直觉(如把 Stop 当"停止/会话结束")推断其语义
  - 目的=保证"会话末尾统一收口且能 AI 判定"这一诉求在平台硬约束下被如实呈现与取舍，而非用错误机制假装满足；手段=当"能 block 拉回的 Stop 是回合级"与"会话级的 SessionEnd 不能拉回"二者不可兼得时，必须显式告知用户这一矛盾并给出取舍方案，不得把 per-turn 的 Stop 包装成"会话结束统一处理"
  - 目的=收口幂等游标不能在"尚无反馈"时过早推进而漏掉后续真实反馈；手段=Stop 收口的判定基准应改为"捕获刚处理完的那一轮用户输入是否含对 skill 产物的反馈"，而非以累计 skill 调用条数作为 cursor，避免产物生成当轮即推进游标
