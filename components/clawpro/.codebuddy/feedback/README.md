# ClawPro Skill 反馈提炼与治理规范 (FEC Framework)

> **本规范目的**：建立一套标准化、自进化的 Skill 反馈收集机制。
> **适用对象**：Skill 使用者（PM a/b/c）、Skill 负责人（你）、以及 CodeBuddy AI 助手。
> **存放路径**：项目根目录 `.codebuddy/feedback/README.md`
> **强制执行规则**：`.codebuddy/rules/feedback-rule.md`（全局生效，无需 Skill 内部重复声明）

> ⚠️ **权威来源已迁移（单一源）**：自 `feedback` Skill 建立后，FEC 的**判定标准、落盘规范、反馈单模板**以 `.codebuddy/skills/feedback/` 为**唯一权威**：
> - 判定指南 → `skills/feedback/references/fec-framework.md`
> - 反馈单模板 → `skills/feedback/references/feedback-template.md`
> - 完整流程（含幂等/收口/两种调用模式）→ `skills/feedback/SKILL.md`
>
> 本 README 保留为**框架总览/导读**；下文判定图与模板为历史留档，如与 Skill 不一致，**以 Skill 为准**。

# ⚠️ AI 强制执行声明（不可跳过）

**当用户对任何 Skill 的生成结果提出修改意见、纠错或不满时，AI 必须在修改内容的同一轮对话中同步生成 FEC 反馈文件。这不是可选动作，而是强制流程。**

执行清单：
1. **识别反馈信号**：用户说"不需要""太细节""应该改成""有问题"等
2. **判定象限**：A/B → 生成文件；C/D → 不生成
3. **生成文件**：路径为 `.codebuddy/feedback/{active-skill-name}/{date}-{scene-en-name}.md`
4. **目录不存在则自动创建**：若 `.codebuddy/feedback/{active-skill-name}/` 子目录不存在，直接创建
5. **时机**：与修改内容在同一轮完成，不要"先改文档回头再说"——反馈记录和内容修改是并行动作

> **违反后果**：如果 AI 只修改了内容但没有生成反馈文件，意味着这次优化经验将丢失，相同错误将在后续生成中重复出现。

# 第一部分：FEC 判定指南（必读说明书）

为了防止反馈目录堆满无意义的业务流水账，我们使用 **FEC 2×2 矩阵** 对用户的每条吐槽/修改意见进行四象限划分。只有高价值信号才允许沉淀为文件。

```
               ▲ 影响范围 (Scope)
               │
               │  【象限 B：隐性知识/规则漏洞】    │  【象限 A：系统性 Skill 逻辑缺陷】
               │  （表面是个案，深层是系统漏洞）   │  （显性的通用问题：格式、字数、幻觉）
               │  - 判定：AI 逻辑没有常理，乱编。 │  - 判定：字数太啰嗦、出现技术词、格式太繁复。
               │  - 动作：通过 RCA 转化为 KB 升级。│  - 动作：直接修改通用 Skill 约束。
全局/系统性 ────┼─────────────────────────────────┼────────────────────────────────────────►
               │                                 │
               │  【象限 D：彻底的无价值噪声】     │  【象限 C：纯业务内容微调】
               │  - 判定：拼写错误、情绪宣泄。     │  - 判定：需求的临时决策变更、纯主观润色。
               │  - 动作：【不生成文件，直接丢弃】│  - 动作：【个案修改，不记入 Skill】
               │                                 │
               └─────────────────────────────────┴────────────────────────────────────────►
                                                      特定需求/个案性 (Particularity)
```

### 🚦 四象限处理动作：
* **象限 A (Skill 缺陷)**：**100% 记录**。直接转化为 `SKILL.md` 的全局否定约束（绝对禁止项）。
* **象限 B (知识漏洞)**：**100% 记录**。通过 RCA 根因追溯，补充底座规则，升级 `SKILL.md` 的内置知识库。
* **象限 C (业务微调)**：**不记录**。这属于特定功能开发的个案修改，直接在单次生成的 PRD 文本里改掉即可，**不要**写入 Skill 反馈，避免污染历史。
* **象限 D (垃圾噪声)**：**不记录**。

# 第二部分：反馈单生成模板（空白可复制）

> **生成规则**：当在对话中触发反馈时，AI 或用户应复制以下模板，在 `.codebuddy/feedback/{skill-name}/` 目录下生成一个新文件，命名为 `{date}-{scene-en-name}.md`。

```markdown
# Skill 反馈记录 & 提炼分析

## 一、 基本信息
- **Skill 名称**：{填写当前使用的 Skill，如：requirement-writer}
- **应用场景**：{具体的使用场景，如：管控端集成"龙虾医生" Agent 诊断与修复功能 PRD 生成}
- **记录时间**：{YYYY-MM-DD}
- **用户反馈原文**：
  > "{PM 在对话中的原始修改意见或抱怨，请原汁原味摘录}"

================================================================

## 二、 FEC 判定与归类（核心筛选！）
> 请勾选本次反馈所属的象限，评估其对优化 Skill 的价值。

- [ ] **【象限 A：系统性 Skill 逻辑缺陷】** (价值：⭐⭐⭐⭐⭐)
  *判定依据*：AI 生成的内容存在格式冗余、废话铺垫过多、写了前端组件/API等代码细节、或编造了无根据的 UI 尺寸。
- [ ] **【象限 B：隐性知识/规则漏洞】** (价值：⭐⭐⭐⭐⭐)
  *判定依据*：AI 对 ClawPro 的业务模型（如跨所有者权限）、双端对称交互、或 CVM 底座资源生命周期的理解存在严重漏洞。
- [ ] **【象限 C：纯业务内容微调】** (价值：⭐ - *本项仅作记录，无需修改 Skill*)
  *判定依据*：仅是本次开发任务的业务决策临时微调（如"本期先不做对话修复了"），不代表 Skill 的通用逻辑有问题。
- [ ] **【象限 D：彻底的无价值噪声】** (价值：❌ - *请立即将本文件彻底删除*)
  *判定依据*：拼写纠错、偶发性输入错误、无逻辑的排版微调或无实质建议的抱怨。

================================================================

## 三、 根因追溯 (RCA) 与问题识别
- **Skill 犯了什么错**：{描述 AI 输出不佳的具体表现，如：AI 凭空捏造了 40% 的宽度和 20 分钟的超时逻辑}
- **系统性缺陷根因**：
  - [ ] **信息缺失未留白**：输入中未提及该参数，AI 开启了"自动填充数值"的默认幻觉。
  - [ ] **底座知识断层**：AI 不知道平台底座的真实生命周期/限制。
  - [ ] **角色定位偏移**：思维没有立足于"资深 PM 跨所有者全局运维"视角，而降级为了"普通助理"。
  - [ ] **模板固化**：模板过于死板，无法根据需求复杂度动态裁剪模块。

================================================================

## 四、 转化为 Skill 优化策略（SOP）
> 负责人（你）如何根据此反馈修改 `SKILL.md`？

- **【优化行动项 1】**：{如：在绝对禁止中加入"严禁捏造任何前端 UI 细节参数，无提及一律使用 `⚠️待补充` 占位留白"}
- **【优化行动项 2】**：{如：在知识库中补充"临时诊断 Agent 生命周期为 12 小时无对话自动销毁"}
```

# 第三部分：执行规范补充

## 反馈生成时机

| 场景 | 正确做法 | 错误做法 |
|------|---------|---------|
| 用户提出修改意见 | 修改内容 + 生成反馈文件 **在同一轮完成** | 先改内容，"下次再补反馈" |
| 用户连续提出多条意见 | 合并为一个反馈文件，多条问题列入同一张表 | 每条意见单独一个文件 |
| 用户说"记住这个" | 生成反馈文件 + update_memory | 只 update_memory 不留文件 |

## 目录结构

```
.codebuddy/feedback/
├── README.md                          ← 本文件（FEC 框架说明）
├── {skill-name-1}/                    ← 按 Skill 名称分目录
│   ├── 2026-07-08-scene-a.md
│   └── 2026-07-15-scene-b.md
├── {skill-name-2}/
│   └── ...
```

**规则**：
- 目录名 = Skill 文件夹名（如 `clawpro-operation-guide`、`requirement-writer`、`clawpro-test-suite`）
- 若目录不存在，AI 应在写入文件时自动创建（`write_to_file` 工具会自动创建父目录）
- 文件命名：`{YYYY-MM-DD}-{scene-en-name}.md`，scene 用简短英文描述问题主题

## 与 Skill 源码的关系

| 存放位置 | 内容 | 由谁维护 |
|---------|------|---------|
| `.codebuddy/feedback/{skill-name}/` | 原始反馈记录（FEC 单） | AI 自动生成 |
| Skill 源码 `prompts/` 或 `SKILL.md` | 从反馈中提炼的规则（优化行动项落地） | AI 或 Skill 负责人 |

**流向**：反馈文件 → 提炼通用规则 → 注入 Skill Prompt/SKILL.md → 后续生成自动遵循

> **重要**：反馈文件是"证据"，存在项目级 `.codebuddy/feedback/` 中；Skill 源码中只存"提炼后的规则"，不存原始反馈文件。
