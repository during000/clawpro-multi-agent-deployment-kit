# Skill 反馈记录 & 提炼分析

## 一、 基本信息
- **Skill 名称**：clawpro-operation-guide
- **应用场景**：管控端龙虾医生诊断功能官网操作文档生成
- **记录时间**：2026-07-15
- **用户反馈原文**：
  > "管控端可直接使用龙虾医生能力，无需在「平台策略」中开启，「平台策略」开启只是为了用户端可以使用该能力"
  > "无需介绍功能区信息，过于细节了"
  > "这部分也有一些太细节了，无需展示具体指令"
  > "面板操作也无需额外介绍啊，产品文档中需要着重描写的是功能而不是具体细节，像这种放大缩小的能力不用撰写，作为用户看到相应符号会知道怎么操作的，而且放大缩小适配也并不值得作为一个能力给客户介绍，这是平台需要具备的基础能力"
  > "这种待产品确认的不能出现在产品文档中，这种不确定的宁可不写也不能说待确定，因为产品文档时对客户的，需要严谨专业，不能出现这种迷惑或者不确定的描述"
  > "另外这一部分没有官网文档的连续性，比较分散，更偏向介绍这个功能怎么实现，而不是对外介绍互斥"
  > "诊断会话保持也属于默认支持的基本能力，无需突出给用户展示"
  > "总而言之，当前的产品官网文档很像对内的需求介绍，不太是一个对外的专业的严谨的连贯的产品文档，整体架构较松散，文字连贯性差，需要整体优化。"

## 二、 FEC 判定与归类（核心筛选！）

- [x] **【象限 A：系统性 Skill 逻辑缺陷】** (价值：⭐⭐⭐⭐⭐)
  *判定依据*：AI 生成的文档在结构上过度翻译 PRD 内部细节，缺乏对外产品文档的专业视角过滤能力。这是 Skill 的 Document 阶段 Prompt 中缺失"产品文档 vs PRD 边界"约束导致的系统性问题，会影响所有功能文档的生成质量。
- [x] **【象限 B：隐性知识/规则漏洞】** (价值：⭐⭐⭐⭐⭐)
  *判定依据*：AI 不理解"管控端无需开启即可使用龙虾医生"这一业务逻辑，错误地将用户端的前提条件套用到管控端，暴露了对双端功能权限模型的理解漏洞。

## 三、 根因追溯 (RCA) 与问题识别
- **Skill 犯了什么错**：
  1. 将 PRD 中的内部交互细节（功能区引导文案、按钮状态、斜杠指令列表、面板缩放）原样搬入对外文档
  2. 将"待产品确认"的内部标注暴露给客户
  3. 按实现维度（管控端提示/用户端提示/状态管理规则）拆分互斥章节，而非按用户认知维度组织
  4. 将后台基础能力（会话保持、面板缩放）作为功能亮点单独成章
  5. 错误理解管控端与用户端的功能权限关系，混淆前提条件

- **系统性缺陷根因**：
  - [x] **信息缺失未留白**：PRD 中的"待产品确认"应该被过滤而非原样输出，Skill 缺少"内部标注过滤"规则
  - [x] **底座知识断层**：不清楚管控端龙虾医生的使用无需平台策略开启，仅用户端需要
  - [x] **角色定位偏移**：以"需求文档整理者"视角而非"对外产品文档作者"视角撰写，未站在客户立场过滤信息
  - [x] **模板固化**：dual_role_guide 骨架导致机械地拆分管控端/用户端子章节，缺乏根据实际场景裁剪的灵活性

================================================================

## 四、 转化为 Skill 优化策略（SOP）

- **【优化行动项 1】**：在 `prompts/document/system.md` 新增"产品文档 vs PRD 边界"P0 级约束章节（已完成 v6.3），包含 7 条硬性过滤规则：不写 UI 视觉细节、不写平台基础能力、不写细粒度交互指令、不写内部不确定项、不按实现维度拆分、前提条件需角色确认、连贯性检验
- **【优化行动项 2】**：在 `references/feature-details.yaml` 的 `lobster-hospital` 条目中补充 `admin_prerequisites` 字段，明确标注"管控端无需平台策略开启即可使用"
- **【优化行动项 3】**：在写作铁律中新增第 16 条规则："绝不输出含'待确认''待定''TBD'的内部标注——不确定的内容直接省略，不对客户暴露内部决策状态"
- **【优化行动项 4】**：调整 dual_role_guide 骨架说明——当管控端/用户端操作不对称时（一端为主操作、另一端仅受影响），应以主操作端为主线撰写，另一端仅在关联说明中简要提及，不强制拆分对等章节
