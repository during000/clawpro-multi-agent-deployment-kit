# 设计内部协作手册（ClawPro）

> 这份文档不解释 git，也不展开命令行，只告诉你**什么时间、和 AI（Manus / CodeBuddy）说哪句话**。
> 用法：照着步骤走 → 把每段引号里的话**整段复制**给 AI → AI 会自动完成剩下的事。
> 适用仓库：`openclaw-enterprise`　最近更新：2026-05-13

---

## 〇、先搞清楚我们在哪个体系里

ClawPro 整体走的是产品定的「**特性分支工作流**」：
- **主干 `main`** —— 由 qiting 维护，合并所有人的改动 + 公共基建（路由、Layout、全局样式）。
- **业务特性分支 `feature/admin-*` `feature/tenant-*`** —— 产品/前端的工作区，一个页面一条。

**设计团队不直接对 `main` 工作**，我们有两条专属分支：

| 分支 | 角色 | 谁来推 | 谁可以拉 |
|---|---|---|---|
| `feature/design-refresh-2026` | **设计基线分支**——"对外公认的整站完整版"，所有设计同学都基于它干活 | **设计团队全员均可推**（push / 合 PR），但**推之前必须在群里同步一次**；设计 owner 额外负责每个工作日早上 10 点前同步 main，详见第七节 | 全员，作为参考 |
| `feature/design-花名` | **个人草稿分支**——日常探索、改稿都在这里 | 仅本人 | 任何人可以查看，**不要 push** |

> 命名规则：`feature/design-花名`，例如 `feature/design-jingsujiang`。新人入职时找 owner 帮你建一条。

### 为什么设计要基于 `design-refresh-2026`，不是 `main`？

- `main` 是按"页面/功能"切片的，每位产品/前端同学合进来的只是局部页面；
- 设计同学要看的是**整站完整原型**——这正是 `design-refresh-2026` 的角色：定期把 main 的最新成果全量同步过来，再叠加设计的细节调整；
- 所以**设计同学日常 rebase 的目标是 `design-refresh-2026`，而不是 `main`**。

## 一、设计团队的红线：哪些事**绝对不要做**

> 这一节是整份文档最重要的部分，违反任何一条都可能导致主干被污染、其他同学代码丢失。

1. **不要改 `main` 分支** —— 任何时候都不要直接 push 到 `main`。
2. **不要往别人的 `feature/*` 分支推东西** —— 包括产品/前端的 `admin-*`、`tenant-*`、`landing-page` 这些。要看可以切过去看，**不要改**。
3. **不要在群里没同步的情况下，直接往 `feature/design-refresh-2026` 推东西** —— 这条基线分支设计团队全员均可维护，**但每次推（push 或合 PR）之前必须在群里同步一次**：说清楚要合什么内容、影响哪些页面，没人提异议（或得到回应）后再合。这样能避免你和别的设计同学的改动相互覆盖。
4. **不要动以下"公共基建"**（这是 qiting 的活）：
   - 路由文件 `App.tsx`
   - 用户端导航 `TenantLayout.tsx`、管控端导航 `AdminLayout.tsx`
   - 全局样式
   - **新增子页面、新增子 Tab**
5. **要改路由/导航/新增页面 → 找 qiting**，不要自己动手，也不要让 AI 自己加。
6. **不要把 token、密码、内网地址、真实客户数据写进代码**。mock 用 `user-001`、`xxx@example.com` 这种假数据。

## 一·五、设计系统的「触达即同步」约定（重要）

> 这一节回答一个常见疑问：**"SKILL.md 升级了一版，但仓库里几百个页面是按老版本写的，要不要一次性全刷？"**
> 答：**不要全刷，按"改到哪、刷到哪"的节奏分散消化。**

### 为什么不全刷？

- 一次性批量改大量页面会和别人的 `feature/*` 分支严重冲突，对其他同学不友好；
- 设计系统本身也在持续演进，今天全刷的版本明天又过时；
- 存量违规靠日常迭代覆盖，几个迭代周期下来就会自然消化干净。

### 怎么做？

每次你（或 AI）打开某个页面文件**做任何修改**时，按下面三步走：

1. **先看一眼这个文件是否符合当前 SKILL.md**——
   AI 已经在 skill 的 §0.1「AI 行为约定」里被要求自动做这件事，你不用额外提醒。如果你是手工改的，重点扫：
   - 卡片有没有用 `<SurfaceCard>` / `<SurfaceConfig>` 等语义组件，而不是手写 div + `box-shadow`
   - inline `boxShadow` 有没有改成 `var(--shadow-*)` 变量
   - 主色还在不在用老的 `#007AFF` / 蓝紫渐变
   - 圆角有没有超过 `rounded` (4px) 这一档
2. **顺手把违规刷掉**——和你本次的主诉需求一起提交，不用单独开 PR。
3. **改完跑一下自检**：`node scripts/check-card-shadow.cjs`，确保至少没引入新违规。

### 如果 AI 提示某个文件违规很多、刷新工作量比主诉还大？

让 AI 列出违规清单 + 预估改动量，三选一：
- **本次只做主诉**：违规留给后人（或下次自己再来时）；
- **一起刷**：你接受时间成本，授权 AI 一并改完；
- **单独排期**：作为独立任务记进 todo / Tapd，专门留一个时段处理。

### 给 AI 的一句话提示模板

如果你担心 AI 没做检查，可以在 prompt 里加一句：

> "改完 XXX 之后，按当前 SKILL.md 的标准把这个文件里其他不合规的地方一起刷一下。"

> 但通常**不需要**——skill 加载后这个机制已经默认开启。

### 当前存量快照（2026-05-14）

- `box-shadow` 违规 196 处、约 50 个文件；
- 不做集中清理，按本节约定随日常迭代消化；
- 详见 `chats/by-topic/design-system-card-shadow.md`。

## 二、看一眼分支总表，定位你要改什么

完整 34 条业务分支表见产品手册《二、全部分支汇总表》。设计同学最常打交道的是：

| 你想改的页面 | 对应业务分支 | 负责团队 |
|---|---|---|
| 落地页 | `feature/landing-page` | 计算 |
| 我的 OpenClaw / OpenClaw 详情各 Tab | `feature/tenant-openclaw-detail-*`、`feature/tenant-my-openclaw` | 计算 / 数据库 / 云盘 |
| 技能广场、模型配额、帮助文档 | `feature/tenant-skill-square` 等 | 计算 |
| 管控端基础信息 / 用户管理 / 模型 / 通道 / 平台策略 | `feature/admin-基础信息` / `admin-member-management` 等 | 计算 |
| 管控端记忆/文件/网络/云开发/安全/审计 | `feature/admin-memory-management` 等（按表查） | 数据库 / 云盘 / 云开发 / 安全 |
| 管控端 OpenClaw 列表 / 智能体迁移 | `feature/admin-openclaw-monitor` / `feature/admin-agent-migration` | 计算 |

> ⚠️ **设计同学一般不直接在业务分支上改稿**——业务分支是产品/前端的工作区。
> 我们的工作模式是：**在自己的 `feature/design-花名` 分支里做高保真探索 → 评审通过 → 输出 PRD → 由对应模块的产品/前端在他们的业务分支落地**。
> 如果某次特别紧急，需要设计直接动业务分支的代码，**先和 qiting 确认**再开干。

### 2.1 像 Figma 一样做版本管理（重要）

设计同学日常会有大量探索稿——三个对比稿、被否的方案、还在打磨的实验……和 Figma 里 V1 / V2 / V3 / 终稿一个意思。我们用**文件夹**把这些版本平铺管理，操作和 Figma 一模一样。

#### 目录约定

所有探索稿统一放在 `_designer-drafts/` 顶层目录下，**第一层永远是你的英文 ID**：

```
_designer-drafts/
├── js/                    ← 你的英文 ID（jingsujiang → js）
│   ├── 登录页/
│   │   ├── v1-玻璃拟态/
│   │   ├── v2-极简白底/
│   │   ├── v3-插画风/
│   │   └── final/        ← 评审定下来这版（v3 复制过来），准备落地
│   └── 用户管理页/
│       ├── v1-表格紧凑版/
│       └── final/
├── qt/                    ← 其他同学的（qiting → qt）
└── ...
```

| 层级 | 含义 | 命名规则 |
|---|---|---|
| 第 1 层 `_designer-drafts/` | 探索稿总目录 | 固定，不要改 |
| 第 2 层 `js/` `qt/` | **你的英文 ID**（避免不同同学撞名/冲突） | 2~6 个字母小写，由 owner 统一分配 |
| 第 3 层 `登录页/` | 你正在做的页面/模块 | 中文，和实际页面名一致 |
| 第 4 层 `v1-玻璃拟态/` | 具体某个版本 | `v1-方向描述` `v2-方向描述`... 评审定下来的复制成 `final/` |

> 💡 **英文 ID 没什么神秘的**：就是把花名缩写一下，方便机器识别、避免中文路径偶尔出问题。你的英文 ID 在分支名 `feature/design-jingsujiang` 里也用不到——分支名用全花名，目录用缩写。**没分配过的同学找 owner 要一个**。

#### 关键约定

- ✅ **每个版本是独立文件夹**，互不覆盖，全部保留历史。
- ✅ **评审定稿时**：把定下的那版**复制**一份到 `final/`，**原 v1/v2/v3 都不要删**，方便以后回看演变。
- ✅ **正式落地时**：让 AI 把 `final/` 里的内容搬到正常页面路径下，发 PR。
- ❌ 不要在 `_designer-drafts/` 之外的地方放探索稿。
- ❌ 不要动别人的 `_designer-drafts/xx/` 目录。

#### 工作流：从开探索到落地的完整例子

> 场景：jingsujiang（英文 ID `js`）要重新设计登录页，探索 3 个方向后选定一版落地。

| 阶段 | 复制这句给 AI |
|---|---|
| 1. 开第一个探索 | "我要做登录页改版，探索玻璃拟态方向，叫 v1。请把所有新文件放到 `_designer-drafts/js/登录页/v1-玻璃拟态/` 下。不要动正常路径下的登录页。" |
| 2. 开第二个探索 | "再做一版，极简白底方向，叫 v2。放到 `_designer-drafts/js/登录页/v2-极简白底/`。" |
| 3. 开第三个探索 | "再做一版，插画风方向，叫 v3。放到 `_designer-drafts/js/登录页/v3-插画风/`。" |
| 4. 评审通过 v3 | "v3 评审通过了。把 `_designer-drafts/js/登录页/v3-插画风/` 整个**复制**一份到 `_designer-drafts/js/登录页/final/`。**v3 原目录保留**，不要删。" |
| 5. 落地到正式路径 | "把 `_designer-drafts/js/登录页/final/` 里的内容搬到正常的登录页路径下（替换原文件），然后帮我发 PR 到 `feature/design-refresh-2026`。" |

> 第 5 步发 PR 的时候，**`_designer-drafts/` 整个目录都不要进 PR**——只把"搬到正常路径"这一步的改动打包发出去。详见 6.2。

## 三、第一次开工：建立你的 AI 工作区（只做一次）

### 步骤 1 —— 在 CodeBuddy（推荐）或 Manus 里新建项目

> 推荐用 CodeBuddy，公司承担 token 费用。

新建一个对话项目，把下面这段**整段复制**给 AI（替换花名）：

> 我们采用 feature 分支工作流开发 ClawPro 网站。请帮我克隆 `https://github.com/tx-organization/openclaw-enterprise` 仓库，切换到 `feature/design-花名` 分支，并 rebase **`feature/design-refresh-2026`** 分支代码（这是设计基线分支，包含整站完整原型）。我会在这个分支上做设计稿迭代。请帮我启动本地开发服务器。**注意：不要修改 `App.tsx`、`TenantLayout.tsx`、`AdminLayout.tsx`，也不要新增页面或 Tab。**

把"花名"换成你自己的，比如 `feature/design-jingsujiang`。

### 步骤 2 —— GitHub 授权

AI 一般会让你授权登录 GitHub。授权细节（PAT 怎么给、怎么处理"分支不存在"的提示）**完全照产品手册《三 · 步骤 2》执行**，这里不重复。

> 如果出现"没有在仓库里找到该分支"，对 AI 说：
> 帮我创建分支 `feature/design-花名`，把当前分支推送到远端。

### 步骤 3 —— 给 AI 喂设计规范（重要）

让 AI 先学我们 ClawPro 独立站的设计规范，再开始干活。复制这句给它：

> 你先学习一下我们的设计规范：`https://drive.weixin.qq.com/s?k=AJEAIQdfAAoJ29M21KADEAmAYdAEk`，后续所有设计稿都要遵守这套规范。

### 步骤 4 —— 打开预览链接，对照 demo 检查

打开 AI 给的预览链接，和官方 demo 对一下：
- 官方 demo：`https://aisite.studio/`（需要找 qiting 申请查看权限）
- 如果你的预览和 demo 差很多，多半是基线分支没同步 → 先在群里看一下 owner 当天有没有发"基线已更新"，没有就 @ owner 同步一次；同步完跳到第四节让 AI 重新 rebase。

## 四、每次开工前：让 AI 同步最新设计基线

> ⚠️ **每天上班第一件事**，以及每次开始一个新需求/新功能时，都要做这一步。
> 因为设计 owner 每天会把 main 同步到 `design-refresh-2026`，其他设计同学也可能有新改动合进基线，你的本地很可能已经过时。

复制这句给 AI：

> 先 rebase 远程的 **`feature/design-refresh-2026`** 分支（这是设计基线），检查是否有冲突；如果有冲突先解决，保留我这边的设计改动不要被基线覆盖。我要继续在 `feature/design-花名` 分支上工作。

> 跑完 AI 会告诉你"已同步"或"已解决冲突"，没问题就可以继续干活。

> 💡 **小贴士**：基线分支由 owner 在每个工作日 10 点前更新，所以建议你**早上 10 点之后**再做这步，能拿到当天最新的基线。

## 五、日常改稿：用大白话和 AI 对话

像平时一样自然语言指令就行，例子：

> 在管控端的"用户管理"页里，把表格右上角的"批量操作"按钮改成下拉菜单样式，参考 Tea 的 Dropdown 组件。

> 帮我把"OpenClaw 详情 - 基础配置 Tab"的页面顶部 Header 调整一下：状态标签放到名称右侧，"一键更新"按钮改成 ghost 样式。

> 📌 上面是直接改"正式页面"的写法（适合改某个已确定的小细节）。
> 如果是想做**版本探索**（多版对比、新方向尝试），改用 2.1 节里的版本管理写法，让 AI 把新文件放到 `_designer-drafts/英文ID/页面名/vN-方向/` 下。

### 5.1 设计同学要特别注意的几个边界

- ❌ **不要让 AI 新增菜单项、新增 Tab、新增路由**。这些找 qiting。
- ❌ **不要让 AI 改 `App.tsx` / `AdminLayout.tsx` / `TenantLayout.tsx`**。如果 AI 主动说要改，**打断它**：
  > 这几个文件不要动，是 qiting 维护的公共文件。我只是想改 xxx 页面里的内容。
- ✅ **只改自己分支对应的页面文件**。不确定要改哪里，先问 AI"这个改动会涉及到哪些文件"，看一眼范围再让它动手。

### 5.2 如果你正好在做这几个特殊页面

如果你在做以下任一页面：**管控端基础信息配置 / 用户管理 / OpenClaw 列表 / Tokens 监控**，开发前额外加一句：

> 这个页面有两种模式，通过 `hasOneid` 区分普通模式和 OneID 专用模式。除非我特别说明，否则所有改动默认对两个模式都生效。

改完记得自己也确认两种模式都生效了。

### 5.3 怎么看自己改的效果

- **CodeBuddy**：本地预览链接，只有自己能看。要给别人看，让 AI 部署到 Lighthouse。
- **Manus**：临时公网链接，所有人能访问；长时间不对话页面会休眠，再发条消息就唤醒。

## 六、改完一段，把进展同步出去

> ⚠️ **划清楚两件事**：
> - **「推到自己分支」= 备份**，每天都要做，不会触发任何主干合并；
> - **「发 PR」= 提议合到设计基线**，只有 final 评审通过时才做。
>
> 你的 `feature/design-花名` 分支就是你的"远端备份盘"，远端会保留你**所有**改动（探索稿、半成品、final 都行），不丢、可恢复、可分享给同事看。

### 6.1 提交前再 rebase 一次（推荐每次推送前都做一次）

为什么要 rebase？因为你做稿的这段时间里，基线分支可能又被 owner 更新过、或别的设计同学合入过新内容。

复制这句给 AI：

> 先 rebase 远程 **`feature/design-refresh-2026`** 分支（设计基线），检查是否有冲突；如果有冲突先解决，注意 rebase 后要**保留我这次的设计改动**，不要被基线覆盖。

### 6.2 情况 1：每日下班前备份（不发 PR）

> 适用：今天没做完、半成品一堆、或者只是想存一下进度。
> 频率：**每天下班前一定要做一次**，养成习惯。换电脑、出问题想恢复都靠它。

复制这句给 AI（按 6.1 rebase 完之后）：

> 我今天先备份一下进度。把当前**所有改动都 commit**（包括 `_designer-drafts/` 下的探索稿、未完成的任何文件），commit 信息写 "WIP：5 月 13 日下班备份"，然后 push 到远端的 `feature/design-花名` 分支。**不要发 PR。**

> 💡 **WIP** = Work In Progress（进行中），是行业惯例的"半成品"标记。AI 看到 WIP 就知道这是临时备份、不打算合主干。

#### 备份后能做什么

- **明天早上接着干**：开工前 rebase 一次基线（第四节），然后继续改；
- **换电脑/出问题想恢复**：让 AI "把 `feature/design-花名` 分支拉下来，启动开发服务器" 即可；
- **想给同事看效果**：把分支名或 AI 给的预览链接发到群里。

### 6.3 情况 2：某个版本评审通过，发布定稿（推 + 发 PR）

> 适用：某个 X 页面的 `final/` 版评审通过了，要正式纳入设计基线。

按 6.1 rebase 完之后，复制这句给 AI（替换 X 页面、英文 ID 和花名）：

> 我要发布"X 页面"的定稿。请帮我做这几件事：
> 1. 把 `_designer-drafts/英文ID/X 页面/final/` 里的内容**搬到正式 X 页面路径下**（替换原文件）；

## 七、设计基线分支的更新机制

这一节解释 `feature/design-refresh-2026` 是怎么"保鲜"的。**全员都需要读 7.1 + 7.2**（合并到基线人人会做），7.3 是 owner 兜底的两件事（同步 main + 周合并）。

### 7.1 普通设计同学需要知道的节奏

| 时间点 | 发生什么 | 你要做什么 |
|---|---|---|
| **每个工作日 10:00 前** | 设计 owner 会把 main 的最新内容同步到 `feature/design-refresh-2026`，并在群里发"基线已更新到 X 月 X 日" | **10 点之后再开工**，开工前按第四节 rebase 一次基线 |
| **你想合 PR 到基线 / 直接推基线时** | **先在群里同步一次**：说清楚改了什么、影响哪些页面 | 没人提异议或得到回应后再合（详见 7.2） |
| **你的 PR 合到基线后** | 你的设计稿就进入了"待打包合 main"的队列 | 不用做任何事 |
| **每周固定一天（建议周五下午）** | 设计 owner 把基线分支累计的所有设计改动**打包**合并到 main，qiting 同步到 demo | 在群里关注 owner 的合并通报 |
| **临时紧急合 main** | 极少见，由 owner 决定是否走加急 | 等 owner 通知 |

### 7.2 任何设计同学要把改动合到基线时的清单

设计团队全员都可以把自己的改动合到 `feature/design-refresh-2026`（直接 push 或 PR 都行），但**合并之前必须先在群里发一条同步消息**，让其他人知道你要合什么。

#### 步骤一：群里同步（合并前必做）

在设计群里发一条消息，至少包含三块信息：

> 📣 我准备把 `feature/design-花名` 上 X 页面的 final 改动合到 `design-refresh-2026`：
> - 改了哪些页面：登录页 / 我的 OpenClaw 详情页（OneID 双模式都改了）
> - 是否动了别人也在改的文件：（如有，@ 对方）
> - 预计合并时间：今天下午 16:00 前
> 有异议或冲突随时叫停我，没人回应我就直接合了。

#### 步骤二：自检清单（合并前必过）

合之前自己先 review 一遍：

- [ ] 改动是否只涉及对应页面文件，没动 `App.tsx` / `Layout` / 路由？
- [ ] 是否符合设计规范（参考 SKILL.md，含 §0「触达即同步」）？
- [ ] 改动有没有把别人的设计稿覆盖掉？（在 PR diff 里仔细看一遍）
- [ ] 涉及 OneID 双模式的页面，是否两种模式都改了？
- [ ] **`_designer-drafts/` 下的内容跳过 review**（那是同学的探索稿历史，作为备份一起推上来的，不影响 main，到周合并时会统一剔除）。

#### 步骤三：合并

- 走 PR：在 GitHub 点 **Confirm merge**，目标分支 `feature/design-refresh-2026`
- 直接 push：`git push origin feature/design-refresh-2026`（确保是 fast-forward，不要 force push）

合完在群里回一条："✅ 已合入基线，commit hash xxx"。

#### 何时仍要找 owner？

- 涉及大范围跨页面改动（如设计系统升级，本次的 SKILL.md 升级就属于这类）：建议让 owner 帮忙 double-check 一次再合
- 出现 rebase 冲突自己解不了：@ owner 协助
- 不确定改动是否会破坏其他同学的设计稿：先在群里 @ owner 走一次评审

## 九、文档与素材放哪里

| 类型 | 位置 | 命名 |
|---|---|---|
| PRD / 交互说明 | `docs/` | `PRD_模块_功能.md`，参考 `PRD_ADMIN_AGENT_DRAWER_EDIT.md` |
| 设计规范 / 协作流程 | `docs/` | 大写下划线，如 `DESIGN_COLLAB_GUIDE.md` |
| 截图 / 对比图 / 视频 | **不要放仓库** | 放共享网盘，文档里贴链接 |
| **定稿**：高保真页面代码 | `app/(admin)/...` 或 `app/(tenant)/...` | 沿用前端现有结构 |
| **探索稿**：多版本对比 / 实验 | `_designer-drafts/英文ID/页面名/vN-方向/` | 评审通过的复制成 `final/` |

写 PRD 用 `docs/PRD_ADMIN_AGENT_DRAWER_EDIT.md` 当模板，结构是：背景 → 目标 → 范围 → 详细交互 → 边界情况 → 验收标准。
