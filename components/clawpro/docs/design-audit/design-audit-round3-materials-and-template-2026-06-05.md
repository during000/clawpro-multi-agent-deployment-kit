# ClawPro 第三轮审计素材清单与正式报告模板

## 文档定位

这份文档用于启动第三轮审计时统一口径，解决三个问题：

1. 第三轮审计到底要补什么，不与前两轮重复。
2. 启动第三轮前，团队必须准备哪些素材。
3. 正式报告应该按什么结构产出，才能同时回答“线上运行态、规范冲突、组件使用”三个维度的问题。

## 第三轮审计的目标

前两轮审计已经回答了：

- 文档之间是否打架
- 共享组件实现与文档是否冲突
- 业务代码是否绕开共享组件

第三轮审计要补的是运行态维度，核心目标应定义为：

“以现网或准现网部署版本为基线，对比规范文档、demo 分支实现、现网运行效果，给出当前组件使用情况、规范冲突的真实影响范围，以及下周换皮/合并后最需要优先治理的对象。”

因此，第三轮不是简单复读前两轮，而是做四方比对：

- 文档规范
- `feature/design-refresh-2026` demo 基线
- 现网或准现网部署版本
- 实际业务使用与运行截图

## 第三轮启动前的必备素材

没有以下素材，不建议启动正式第三轮审计，否则报告会再次停留在“代码静态判断”，无法正式代表运行态结论。

| 素材 | 是否必需 | 提供方建议 | 用途 | 说明 |
|------|----------|------------|------|------|
| 部署环境 URL | 必需 | 开发 / 运维 | 作为运行态基线 | 最好是固定可访问环境 |
| 环境说明 | 必需 | 开发 | 说明是现网、预发还是 demo 部署 | 必须写清楚环境身份 |
| 构建对应 commit / tag / 构建号 | 必需 | 开发 | 锁定运行态版本 | 否则无法与分支代码准确对应 |
| 可登录账号与权限矩阵 | 必需 | 产品 / 开发 | 覆盖 Tenant/Admin 页面 | 至少要有管理员、普通用户、受限账号 |
| 本轮换皮 / 合并范围清单 | 必需 | 产品 / 开发 | 确定审计页面范围 | 说明哪些模块在本轮范围内 |
| 目标 demo 基线 commit | 必需 | 设计 / 开发 | 对比 `feature/design-refresh-2026` | 必须指定唯一基线 |
| 规范文档版本 | 必需 | 设计 | 锁定被审计文档版本 | 防止报告期间文档继续变更 |
| 关键页面清单 | 必需 | 产品 / 设计 | 保证样本覆盖 | 包含首页、列表、详情、表单、弹窗、空态等 |
| 关键组件清单 | 必需 | 设计 | 保证组件覆盖 | 至少包含高风险组件 |
| 截图采集规则 | 必需 | 设计 | 统一证据格式 | 统一分辨率、浏览器、缩放比 |
| 已知例外清单 | 推荐 | 开发 / 设计 | 避免误报 | 如历史模块暂不纳入整改 |
| Figma / 设计稿链接 | 推荐 | 设计 | 补充视觉意图 | 只作为辅助，不替代代码真源 |
| 用户流程脚本 | 推荐 | 产品 | 保证审计可复现 | 例如从登录到下单的标准路径 |

## 建议补充的截图与录屏素材

为了让第三轮报告不仅能判断“代码怎么写”，还能判断“页面实际呈现是否失真”，建议按以下维度收集截图或录屏。

### 页面级素材

- Tenant 首页
- Tenant 列表页
- Tenant 详情页
- Tenant 表单页
- Admin 列表页
- Admin 详情页
- Admin 配置页
- 至少一个复杂弹窗流程
- 至少一个复杂表格流程
- 至少一个空状态 / 错误态 / 加载态

### 组件级素材

- Button：默认、hover、disabled、loading
- Input / Select / DatePicker：默认、focus、error、disabled
- Dialog / Drawer：打开态、关闭动作、标题区、底部操作区
- Table：表头、操作列、分页、空态、滚动、固定列
- Card：Tenant 卡、Admin 卡、共享卡
- Tabs / Segment：选中态、未选中态、切换动效
- StatusTag / Badge：不同语义色、不同模式
- Tooltip / Popover：触发方式与内容形态
- AdminSidebar：展开、收起、选中、hover、底部账户区

### 证据要求

- 每张截图应标明页面路径、账号身份、环境、时间
- 同类页面尽量保持相同窗口宽度
- 若为响应式页面，至少保留桌面端与移动端各一组
- 若无法提供截图，至少提供录屏或页面 DOM 访问方式

## 第三轮正式报告应该回答的问题

正式报告至少要回答以下八个问题：

1. 当前运行态基线到底是哪一个环境、哪一个 commit。
2. 现网与 demo 基线相比，哪些页面已经接近统一，哪些页面仍明显分叉。
3. 当前运行态中，哪些共享组件已经被稳定使用，哪些仍被业务绕开。
4. 当前运行态中，哪些 token 已稳定落地，哪些仍存在新旧并存。
5. 文档冲突是否已经在运行态中造成真实问题，而不是停留在纸面冲突。
6. 下周换皮 / 合并中，哪些模块最值得优先治理。
7. 哪些问题属于规范文档修订，哪些属于共享组件重构，哪些属于业务页整改。
8. 是否已经具备“作为团队后续扩展依据”的条件；若未具备，缺口在哪里。

## 正式报告结构建议

建议第三轮正式报告仍然保留单文档结构，但内部必须分层，不能只做截图集合。

推荐结构如下：

1. 检测基线
2. 核心结论
3. 审计范围与证据来源
4. 运行态总览
5. 规范冲突在运行态的体现
6. 组件使用与收敛情况
7. token 落地与硬编码情况
8. Tenant / Admin 分端判断
9. 优先级整改清单
10. 附录与证据索引

## 严格版结论口径

第三轮报告中的结论，不建议使用“看起来像”“感觉更接近”这类松散描述。建议把结论统一分成四类：

- `已对齐`：文档、代码、运行态基本一致
- `部分对齐`：主体一致，但仍有局部绕开或数值漂移
- `冲突未收敛`：文档、代码、运行态之间存在实质矛盾
- `无法判定`：素材不足或页面未纳入本轮范围

## 问题分级建议

建议第三轮报告按 `P0 / P1 / P2` 分级，而不是只按页面罗列。

- `P0`：继续放任会扩大规范分叉，或会误导后续新功能继续沿用旧标准
- `P1`：影响主流程一致性，但不立即阻断规范框架
- `P2`：历史残留问题，可纳入后续专项治理

## 第三轮报告与前两轮的关系

第三轮报告不应推翻前两轮，而应建立在前两轮之上：

- 第一轮负责说明规范为什么打架
- 第二轮负责说明组件、共享实现、业务使用为什么没有完全对齐
- 第三轮负责说明这些冲突和偏差在运行态上到底造成了什么实际后果

只有这样，最终结论才足够完整。

## 启动第三轮前的建议动作

建议在正式审计前先完成以下准备：

1. 锁定唯一运行态环境，不要同时混用多个预发或个人部署环境。
2. 锁定唯一 demo 基线 commit，不要用“最近几次改动”的模糊口径。
3. 锁定本轮页面范围，不要无限扩展到所有历史模块。
4. 先收齐账号、截图规则、例外清单，再开始审计。
5. 在报告首页明确写清楚“第三轮回答什么，不回答什么”。

## 本文结论

第三轮正式审计要成立，必须先拿到运行态素材，而不只是继续看代码。

对团队来说，最关键的不是“再出一份更长的报告”，而是：

- 用统一素材口径保证证据有效
- 用统一模板保证结论可比较
- 用统一分级让产品、设计、开发都能据此安排后续工作

这份文档的作用，就是把第三轮审计从“临时补截图”提升为“可正式对齐项目组的运行态审计”。
