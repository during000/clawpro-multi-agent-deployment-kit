# ClawPro 规范收敛框架与下周团队交付建议

## 文档定位

这份文档回答两个问题：

1. 基于当前已经完成的两轮审计，是否已经可以对“规范如何收敛、下周设计团队应交付什么”直接下结论。
2. 如果下周需要向产品、开发、项目组其他成员正式交付一套可执行依据，交付物应当如何组织，分别承载什么内容。

本文件不是第三轮运行态审计报告，也不替代组件规范正文；它是当前阶段的治理结论与交付建议。

## 结论边界

## 可以直接下结论的部分

基于以下材料，已经足够对“规范框架应该怎么收敛”直接下结论：

- [design-spec-conflict-audit-2026-06-05.md](docs/design-audit/design-spec-conflict-audit-2026-06-05.md)
- [design-component-compliance-audit-2026-06-05.md](docs/design-audit/design-component-compliance-audit-2026-06-05.md)
- `feature/design-refresh-2026` 分支的共享 token、共享组件、Tenant/Admin 页面实现态

原因很明确：

- 当前最大问题首先是规范仲裁关系混乱，而不是缺一轮运行态截图。
- 是否应该“一份文档”还是“多份文档分层”，本质取决于规范职责划分，而不是取决于线上截图。
- 哪些组件已经可以作为真源、哪些组件必须先专题治理，这在代码与前两轮审计中已经有充分证据。

## 暂时不能直接下结论的部分

以下结论仍需要第三轮运行态审计才能正式下：

- 现网部署页面与 `feature/design-refresh-2026` demo 的逐页视觉偏差范围
- 现网是否仍保留更多历史组件、裸样式、旧 token 残留
- 哪些模块在下周“换皮/合并代码”后会立即受益，哪些模块仍需额外重构
- 团队是否可以对外声明“线上已基本完成组件化和 token 化”

因此，第三轮审计不是为了决定规范框架本身，而是为了判断“现网离这套框架还有多远”。

## 核心结论

1. 下周设计团队不应交付“一份巨大的总规范文档”。
2. 更合理的交付物是“一套分层规范包”，由 `1` 份总入口、`2` 份规则文档、`2` 份治理附件组成。
3. `SKILL.md` 不应继续承载具体 token 数值、尺寸、圆角、品牌色、组件细节；它只适合作为总入口与治理说明。
4. `SKILL-GLOBAL-COMPONENTS.md` 不应直接原样保留为最终标准；应改造成共享组件目录与使用规则文档，删除容易漂移的硬数值，并对高风险组件做明确裁决。
5. `SKILL-TENANT.md` 应缩成 Tenant 差异补充文档，只保留 Tenant 相对共享基线的差异规则，不再重复整套共享组件说明。
6. 设计团队下周真正要交付给项目组的，不只是“规范文本”，而是“可执行的仲裁关系 + 组件真源映射 + 高风险组件裁决 + 迁移优先级”。

## 建议的最终规范框架

建议采用“`1 + 2 + 2`”结构，而不是单文档结构。

### 1. 总入口文档

建议继续使用 `SKILL.md`，但职责必须收窄为：

- 说明规范加载顺序
- 说明各文档职责边界
- 说明代码真源位置
- 说明哪些组件/模块仍在治理中
- 说明 AI / 开发 / 设计在执行时应如何仲裁冲突

`SKILL.md` 不再直接写：

- 品牌色 hex 值
- 圆角尺寸表
- 组件视觉数值细节
- 旧字体体系
- 任何可能再次与代码分叉的静态 token 数值

### 2. 共享 / Admin 规范文档

建议保留 `SKILL-GLOBAL-COMPONENTS.md`，但重写为“共享组件说明文档”，职责是：

- 定义共享组件清单
- 定义每个组件的用途、禁用场景、推荐用法
- 给出少量稳定的使用规则
- 明确对应代码真源文件
- 对 Table、Card、Dialog、StatusTag、AdminSidebar 等高风险组件给出裁决

这份文档不适合继续保留大量容易漂移的内容：

- 过多硬编码尺寸
- 与 `index.css` / `ui` 组件不同步的 token 表
- 一份文档中同一组件出现两套规范
- 兼容历史写法但未明确废弃时间的描述

### 3. Tenant 差异文档

建议保留 `SKILL-TENANT.md`，但只保留 Tenant 差异规则，例如：

- Tenant 独有的按钮变体
- Tenant 卡片体系与共享卡片体系的分流
- Tenant Typography 使用要求
- Tenant 特有的表单、导航、空状态、营销视觉规则

不建议继续在这份文档里重复：

- 共享组件的完整说明
- 全局 token 全量表
- 与 `SKILL-GLOBAL-COMPONENTS.md` 重复的基础规则

### 4. 高风险组件裁决清单

建议新增一份短文档，建议名称类似 `DESIGN-COMPONENT-DECISIONS.md`，只处理高风险仲裁。

至少应覆盖：

- Table
- Card / SurfaceCard / TenantCard
- Tabs / Segment / LineTabs
- Dialog / Drawer
- StatusTag
- AdminSidebar
- Typography

每个组件只回答五件事：

- 当前真源是什么
- 当前文档哪里失真
- 当前业务哪里绕开
- 接下来统一到哪一种写法
- 历史写法何时废弃

### 5. 开发迁移清单

建议新增一份面向开发落地的清单，建议名称类似 `DESIGN-MIGRATION-BACKLOG.md`。

这份文档不写设计原则，只写执行事项：

- 哪些页面必须优先换成共享组件
- 哪些旧 token / 旧 class / 旧渐变必须清理
- 哪些组件允许暂时兼容
- 哪些组件不允许新增旧写法
- 哪些页面在下周换皮阶段必须先完成

如果没有这份清单，开发会知道“规范应该收敛”，但仍不知道“这一周具体先改哪里”。

## 为什么不建议收敛成一份文档

不建议把所有内容压成一份文档，原因不是篇幅问题，而是治理问题：

- 当前冲突本来就来自“职责边界不清”
- Shared/Admin 与 Tenant 本身确实存在差异
- 组件规则、治理规则、迁移任务属于三种不同类型信息
- 把真源、差异、迁移、历史兼容全部混在一起，很容易再次产生第二轮冲突

如果团队只有一份大文档，短期看像是统一，长期通常会再次分叉：

- 设计改一版
- 开发补一版
- AI 再从另一段旧描述里读取出相反结论

这正是当前仓库已经出现过的问题。

## 当前离理想状态还有多远

不建议用单一百分比描述，因为当前问题不是线性进度，而是“不同层级成熟度不同”。更严谨的表达方式是分层判断。

| 层级 | 当前状态 | 判断 |
|------|----------|------|
| 规范仲裁关系 | 三份文档优先级互相冲突 | `未达标` |
| 共享 token / 基础组件实现 | 已有较清晰代码真源 | `接近可用` |
| Tenant 差异体系 | 方向已形成，但落地不完全 | `部分可用` |
| 业务页面组件收敛度 | 仍存在大量绕开共享组件和硬编码 | `未达标` |
| 可直接交付给团队执行的规范包 | 当前还没有完整成型 | `未达标` |

更直接地说：

- 代码侧已经具备“收敛的骨架”
- 文档侧还没有形成“稳定的仲裁框架”
- 业务落地侧还没有形成“严格执行状态”

所以当前不是从 `0` 开始，也不是已经可以直接宣布完成；更准确的状态是：

“组件和 token 的基础能力已经沉淀出主体，但规范治理与业务落地仍差最后一轮收口。”

## 下周设计团队建议交付什么

如果下周你需要代表设计团队向产品和开发做正式交付，建议交付以下六项内容。

### A. 一份总说明

内容应回答：

- 本次设计沉淀解决了什么问题
- 当前规范真源如何分层
- 团队接下来应依据哪几份文档开展工作
- 哪些模块已经可以按规范稳定扩展
- 哪些组件仍在治理中，扩展前需先查裁决清单

这份材料适合用于项目组快速理解整体结论。

### B. 一套规范入口

即上文的“`1 + 2 + 2`”结构：

- `SKILL.md`
- `SKILL-GLOBAL-COMPONENTS.md`
- `SKILL-TENANT.md`
- 组件裁决清单
- 开发迁移清单

### C. 一份高风险组件裁决表

这是本次交付里最关键的执行依据。没有这份表，团队仍会在以下问题上反复争论：

- Table 到底按哪套规范
- Card 到底哪种场景用 4px，哪种场景用 12px
- Dialog 是不是双端共用
- StatusTag 到底统一到哪种 mode
- AdminSidebar 该信代码还是信文档

### D. 一份换皮阶段迁移优先级

建议至少拆成三档：

- `P0`：不改会继续制造规范分叉的组件与页面
- `P1`：本轮换皮应一起迁移的高频页面
- `P2`：可留待后续专题治理的历史页面

### E. 一份“能对什么负责、暂时不能对什么负责”的边界声明

设计团队本轮可以负责的，是：

- 规范框架
- 共享组件标准
- Tenant 差异标准
- demo 分支的设计合理性

本轮暂时不能直接承诺的，是：

- 现网所有页面已经与规范一致
- 所有历史模块已经完成换皮
- 运行态已经不存在硬编码样式

这份边界声明很重要。否则项目组容易把“demo 与规范沉淀”误解成“现网全量已收敛”。

### F. 一份第三轮审计计划

向团队同步：

- 什么时候基于部署环境做第三轮审计
- 需要哪些现网素材
- 报告产出形式是什么
- 第三轮会回答哪些上线判断问题

这样交付就会形成闭环，而不是只停留在“规则已经写好”。

## 建议的工作顺序

如果你接下来要继续推进，建议顺序如下：

1. 先把规范框架定下来，不再继续让三份文档彼此打架。
2. 再为高风险组件出裁决清单，不要先改全文。
3. 再给开发一份迁移优先级，让下周换皮工作有明确落点。
4. 等部署环境与素材齐备后，再补第三轮运行态审计。
5. 最后根据第三轮审计结果回写文档，而不是反过来先写死大量数值。

## 当前建议的对外表述方式

如果下周需要代表设计团队对项目组说明阶段成果，建议采用下面这类口径：

“本轮设计侧已经完成共享组件、Tenant 差异、token 与高风险组件冲突的梳理，形成了可执行的规范收敛框架。当前 demo 分支已经具备作为后续功能扩展参考基线的条件；现网侧仍需结合第三轮运行态审计，确认换皮和合并后的收敛程度。”

这类说法更准确，也更符合当前证据边界。

## 本文结论

可以直接下结论：

- 规范最终不应收敛成一份大文档
- 设计团队下周应交付的是“分层规范包 + 组件裁决 + 迁移清单”，而不是一份单纯的设计说明
- 当前最适合承担真源职责的是 `index.css + shared ui 组件 + 收敛后的规范文档组合`

不能直接跳过第三轮审计的部分是：

- 现网到底和这套规范差多远
- 哪些历史模块在合并后仍会暴露运行态偏差

因此，下周最佳交付不是“宣称已经全部完成”，而是“正式交付一套可以指导后续页面和模块继续落地的依据”。
