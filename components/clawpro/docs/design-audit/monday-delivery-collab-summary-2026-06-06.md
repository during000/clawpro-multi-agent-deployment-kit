# ClawPro 周一交付协作结论摘要

> 这份文档用于发给同事或同事的 AI，快速同步我们当前对“下周一交付什么、为什么这样交付、怎么分工”的统一结论。
> 日期：2026-06-06

## 1. 当前共识

- 下周一要交付的，不应该只是“设计规范文档”，而应该是一套能直接支持前端一周内换皮的交付包。
- 前端主分支与当前 demo / 设计刷新分支在组件、规范、实现方式上有明显差距，所以不能假设产品前端能直接拷贝 demo 仓代码。
- 仅提供 `clawpro` 项目文件和一个 AI skill 不够，因为产品前端最需要的是“脱离当前 demo 仓后，也知道该怎么还原视觉和交互”的依据。
- 领导提到的 `portable fallback` 是关键。意思不是只告诉对方“现在 demo 里怎么写”，而是要补上“如果没有我们这套组件，也该用原生 HTML/CSS 或现有组件库还原成什么样”。
- 结论上，不建议这次把事情扩成“先做一套正式可安装组件库再交付”。这个方向长期合理，但不适合作为下周一的主交付目标，因为周期太短，而且前端换皮意愿不高，优先级应放在低摩擦落地。

## 2. 这次交付的目标不是做什么

- 不是先做一个完整的 npm 包 / 可发布设计系统。
- 不是先把所有历史页面全部组件化、token 化。
- 不是让产品前端必须迁移到我们 demo 分支的全部基础设施。
- 不是只交一堆原则性设计规范，让开发自己二次理解。

## 3. 这次交付真正要解决的问题

- 让产品前端明确：每类页面最终应该长什么样。
- 让产品前端明确：优先复用什么，实在复用不了时最低限度怎么还原。
- 让产品前端明确：哪些组件是高风险组件，不能自由发挥。
- 让产品前端明确：客户端、管理端、可能的新落地页分别按哪套规则落地。
- 让设计团队在现实工期内拿出“方便、可靠、明确、少返工”的材料，而不是理想化大工程。

## 4. 建议的交付思路

下周一交付建议采用“交付包”思路，而不是单文件思路。交付包至少包含四层内容：

1. 规范入口
2. 端级规则
3. 高风险组件 portable spec
4. 页面 recipes / 迁移映射 / QA checklist

其中最关键的新增物不是再写一份总规范，而是给关键组件补一层 portable spec。

## 5. 什么是 portable spec

portable spec 是给“不是直接在 demo 仓里开发的人”看的组件说明。它至少要回答：

- 这个组件适用于什么场景。
- 视觉标准是什么。
- 结构 anatomy 是什么。
- 状态有哪些，比如 hover、selected、loading、empty。
- 当前 demo 仓怎么用。
- 如果没有当前 demo 组件，跨仓 fallback 的 HTML/CSS / 现有组件库还原方案是什么。
- 旧页面怎么迁移。
- 明确禁止事项。
- QA 怎么验收。

也就是说，portable spec 不是替代现有组件源码，而是补足“跨仓可执行性”。

## 6. 为什么现在不建议优先做成 shadcn 那种可安装组件库

长期可以考虑，但这周不建议把它作为主目标，原因很直接：

- 你们当前窗口期只有一周。
- 产品前端换皮意愿不高，越重的接入方式越容易被放弃。
- 可安装组件库要同时解决打包、依赖、样式注入、token 注入、版本管理、宿主项目兼容，这已经是另一个项目。
- 就算做了可安装组件库，前端也未必愿意接；而 portable spec + token + 页面 recipe 他们一定用得上。

因此，当前更务实的路线是：

- 周一先交付可执行的 portable design pack。
- 后续如果项目验证有效，再把高频组件逐步沉淀成可安装组件库或多 AI 可用的 skill 版本。

## 7. 关于 skill 的结论

- CodeBuddy 版本的 skill 仍然值得继续做，因为公司内部协作会直接用到。
- 最好同时考虑一份更通用的 portable 版本，尽量减少对 CodeBuddy 特定运行方式的依赖。
- 对 Codex、Cursor 等外部 AI，更适合交付的是“目录清晰、引用明确、可直接读 markdown 的 portable skill 包”，而不是强绑定某个产品格式。

## 8. 端与范围结论

- 管理端：确定需要换皮。
- 客户端：确定需要换皮。
- 落地页：可能新做，也可能是已有页面换皮，所以交付包里最好保留 landing 规则，但优先级低于客户端和管理端。

## 9. 角色边界结论

- 设计团队负责：设计规范、组件规范、视觉排版、体验层面的还原标准。
- 设计团队不负责：在不影响功能前提下的具体业务逻辑改造。
- 前端团队负责：在宿主仓里用他们可接受的方式完成换皮实现。
- 因为前端实现意愿一般，所以设计交付要尽量替他们减少判断成本和返工成本。

## 9.1 Spec 收口原则

周一前的组件 spec 策略不是“能补多少补多少”，而是先收口再扩张。

统一原则：

- 先冻结当前已经覆盖的高风险 spec 主范围，不做无序扩张。
- 新增 spec 只在两个条件同时满足时才继续补：一是前端下周换皮高频会遇到，二是不引入新的设计拍板风险，或者已经由当前设计负责人确认。
- 如果只是“也许以后会用到”“理论上也该有”，但本周前端未必会碰到，就先不写。
- 当前阶段更重要的是把已有 spec 写得更稳、更能落地，而不是把目录继续铺大。
- 如果后续要继续扩 spec，优先顺序应基于真实换皮阻塞，而不是按组件库完整度推进。

## 10. 周一前最现实的产出优先级

P0：必须有

- 一份交付包目录结构说明
- 一份总入口 README / SKILL
- Admin / Tenant / Landing 三份端级参考
- 3 到 5 个最关键的高风险组件 portable spec 模板化成文
- migration map
- QA checklist
- 一条明确的范围控制原则：周一前先冻结主 spec 范围，不做无序扩张

P1：强烈建议有

- token 清单
- icon / asset registry
- 1 到 2 个典型页面 recipe，比如管理端列表页、管理端空页面、客户端卡片列表页
- 给 AI 的调用说明

P2：可后补

- 更完整的组件全量 portable spec
- 多 AI 平台适配说明
- 真正可安装的组件库

## 11. 目前最该先做的高风险组件

建议优先补这几个，因为它们最容易在换皮时走样：

- Table
- Card / Surface
- Button
- Empty State
- Page Header / Filters

如果时间还有余量，再补：

- Dialog / Drawer
- Tabs / Segment
- StatusTag / Badge
- Form Field / Input / Select

补充原则：这里的“再补”不是默认全补，而是按真实换皮阻塞决定；没有明确落地价值的 spec，本周先冻结。

## 12. 当前是否已经可以下结论

可以。原因不是“所有规范已经完全正确”，而是“对下周一该交什么”这个问题，已经有足够证据下结论。

现阶段已经足够明确的事实：

- 现有规范文件、组件源码、页面实现之间存在冲突。
- 单靠当前 skill 和 demo 仓源码，不足以支撑前端低摩擦换皮。
- 交付重点应从“继续补总规范”转向“形成 portable delivery pack”。
- 周一期限下，最务实路线不是组件库化，而是补 portable spec、迁移映射和 QA。

## 13. 与同事协作时的统一口径

如果同事或同事的 AI 参与这项工作，统一口径如下：

- 目标不是写更厚的规范，而是让产品前端能最快、最稳地换皮。
- 所有新增材料优先服务“跨仓可执行性”。
- 组件说明必须补 portable fallback，不能只写 demo 仓组件名。
- 优先收口高风险组件，不追求一周内覆盖所有组件。
- 周一前默认冻结主 spec 范围，不为了“看起来完整”继续无序拆新 spec。
- 如果要新增 spec，必须先判断它是不是前端这周高频真会遇到、且不会引入新的设计拍板风险。
- 输出材料要能同时服务人类、CodeBuddy 和通用 AI 阅读。
- 全局组件、管理端规范、以及任何需要设计拍板的问题，统一由你确认，不由协作者或 AI 自行裁决。
