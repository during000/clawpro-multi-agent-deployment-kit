# ClawPro 设计内部协作手册（精简版）

> 本文档是给设计同学看的简化版 + 边界说明，完整版（含 owner 操作）见 `docs/DESIGN_COLLAB_GUIDE.md`。
> 用法：照着步骤走 → 把每段引号里的话**整段复制**给 AI → AI 会自动完成剩下的事。
> 适用仓库：`openclaw-enterprise`　最近更新：2026-05-13

---

## 〇、先搞清楚我们在哪个体系里

ClawPro 的整个开发协作模型，是产品同学已经定好的「**特性分支工作流**」（= 一人一条分支，互不打架）：

- **主干分支 `main`** —— 由 qiting 维护，负责合并所有人改动、维护公共基建（路由、AdminLayout、全局样式）。
- **特性分支 `feature/*`** —— 一个功能/一个页面对应一条分支，谁负责谁开发。

> 产品完整版手册见：<https://doc.weixin.qq.com/doc/w3_ADEAmAYdAEkCNrWqC4FC1S528H76n?scode=AJEAIQdfAAojUL2IrhAYQAygZEAMc>
> 这份是设计团队的简化版 + 边界说明。

设计团队在这套体系里有自己的两条专属分支：

| 分支 | 角色 | 谁来推 | 谁可以拉 |
|---|---|---|---|
| `feature/design-refresh-2026` | **设计基线分支**——"对外公认的当前完整版" | 设计 owner（评审通过后才更新） | 全员，作为参考 |
| `feature/design-花名`<br/>例如 `feature/design-jingsujiang` | **个人草稿分支**——日常探索、改稿都在这里 | 仅本人 | 任何人可以查看，**不要 push** |

### 为什么设计要基于 `design-refresh-2026`，不是 `main`？

- `main` 是按"页面/功能"切片的，每位产品/前端同学合进来的只是局部页面；
- 设计同学要看的是**整站完整原型**——这正是 `design-refresh-2026` 的角色：定期把 main 的最新成果全量同步过来，再叠加设计的细节调整；
- 所以**设计同学日常 rebase 的目标是 `design-refresh-2026`，而不是 `main`**。

### 名词解释表（设计同学常见疑惑）

| 名词 | 大白话 |
|---|---|
| 分支 | 一份代码的"独立副本"，你改你的、我改我的，不会撞车。 |
| `main` | 整个项目的"正式版"，所有人最终都要合并到这里。 |
| rebase | 把别人新改的东西"叠到"你的改动底下，让你的改动看起来像基于最新版做的。AI 会自动做。 |
| commit | 把这一步改动"存盘"，相当于 Figma 里的一次版本快照。 |
| push | 把本地存盘的内容"上传"到远端服务器。 |
| PR（Pull Request） | "申请合并"，把你分支的改动正式提议合到另一条分支。 |
| WIP | Work In Progress，半成品标记，看到这个就知道还没做完。 |
| PAT | GitHub 个人访问令牌，相当于"专门给程序用的密码"。 |
| ghost 样式 | 按钮的"幽灵态"——只有边框/文字、没有底色填充。 |
| OneID 双模式 | 同一个页面有两套展示逻辑（普通模式 / OneID 专用模式），代码里用 `hasOneid` 区分。 |

## 一、设计团队的红线：哪些事**绝对不要做**

> 这一节是整份文档最重要的部分，违反任何一条都可能导致主干被污染、其他同学代码丢失。

1. **不要改 `main` 分支** —— 任何时候都不要直接 push 到 `main`。
2. **不要往别人的 `feature/*` 分支推东西** —— 包括产品/前端的 `admin-*`、`tenant-*`、`landing-page` 这些。要看可以切过去看，**不要改**。
3. **不要直接往 `feature/design-refresh-2026` 推东西** —— 这条基线分支的更新必须周知所有人，排除冲突后才可以合并。
4. **不要动以下"公共基建"**（如果一定要动，找 qiting）：
   - 路由文件 `App.tsx`
   - 用户端导航 `TenantLayout.tsx`、管控端导航 `AdminLayout.tsx`
   - 全局样式
   - **新增子页面、新增子 Tab**
5. **要改路由/导航/新增页面 → 找 qiting**，不要自己动手，也不要让 AI 自己加。
6. **不要把 token、密码、内网地址、真实客户数据写进代码**。mock 用 `user-001`、`xxx@example.com` 这种假数据。

## 二、创建本地项目：建立你的 AI 工作区（重要）

### 2.1 在自己电脑上手动建一个项目文件夹

建议**自己手动新建**文件夹放在你喜欢的位置。如果直接用 CodeBuddy 新建，文件夹会被建到 CodeBuddy 默认目录下，后期挪动可能引发数据问题。

### 2.2 把文件夹拖进 Vibe Coding 工具

推荐使用 **CodeBuddy** 或 Claude 插件，**不建议使用 Workbuddy**（不支持本仓库的 git 工作流）。

CodeBuddy 一个窗口就是一个文件夹（项目）：
- 如果你电脑上已经开了一个 CodeBuddy 窗口，请**新建窗口**打开你刚刚创建的文件夹；
- 或者直接把文件夹拖到 CodeBuddy 头上就能打开这个项目；
- 顶部显示文件夹名称了，就表明成功打开了。

## 三、第一次开工：拉取远程仓库并创建分支

### 步骤 1 —— 在 CodeBuddy 里新建对话项目

推荐用 CodeBuddy，公司承担 token 费用。

新建一个对话项目，把下面这段**整段复制**给 AI（替换花名）：

> 我们采用 feature 分支工作流开发 ClawPro 网站。请帮我克隆 `https://github.com/tx-organization/openclaw-enterprise` 仓库，然后切换到 `feature/design-花名` 分支（例如 `feature/design-jingsujiang`）。**克隆和切分支完成后，再单独执行一步：rebase `feature/design-refresh-2026` 分支**（这是设计基线，包含整站完整原型）。我会在这个分支上做设计稿迭代。请帮我启动本地开发服务器。**注意：不要修改 `App.tsx`、`TenantLayout.tsx`、`AdminLayout.tsx`，也不要新增页面或 Tab。**

把"花名"换成你自己的，比如 `feature/design-jingsujiang`。

> 💡 为什么拆成两步：克隆 + 切分支 + rebase 一次性给 AI 容易出错（远端分支可能不存在、本地还没初始化），拆成"先把项目搭好、再拉基线"成功率更高。

### 步骤 2 —— GitHub 授权

AI 一般会让你授权登录 GitHub。授权细节（PAT 怎么给、怎么处理"分支不存在"的提示）**完全照产品手册《三 · 步骤 2》执行**，链接见〇节顶部。

如果发现拉不下来、显示 PAT 风险拦截等问题，可以临时切换到 CodeBuddy 内置的国内模型（如 Kimi）来完成克隆这一步。

如果出现"没有在仓库里找到该分支"，对 AI 说：
> 帮我创建分支 `feature/design-花名`，把当前分支推送到远端。

### 步骤 3 —— 给 AI 喂设计规范（重要）

让 AI 先学我们 ClawPro 独立站的设计规范，再开始干活。复制这句给它：

> 你先学习一下我们的设计规范：`https://drive.weixin.qq.com/s?k=AJEAIQdfAAoJ29M21KADEAmAYdAEk`，后续所有设计稿都要遵守这套规范。

### 步骤 4 —— 打开预览链接，对照 demo 检查

打开 AI 给的预览链接，和官方 demo 对一下：

- 官方 demo：<https://aisite.studio/>（需要找产品负责人 qiting 申请查看权限）
- 如果你的预览和 demo 差很多，多半是基线分支没同步 → 先在群里看一下 owner 当天有没有发"基线已更新"，没有就 @ owner 同步一次；同步完跳到第四节让 AI 重新 rebase。

## 四、每次开工前：让 AI 同步最新设计基线

> ⚠️ **每天上班第一件事**，以及每次开始一个新需求/新功能时，都要做这一步。
> 因为设计 owner 每天会把 main 同步到 `design-refresh-2026`，其他设计同学也可能有新改动合进基线，你的本地很可能已经过时。

复制这句给 AI：

> 先 rebase 远程的 **`feature/design-refresh-2026`** 分支（这是设计基线），检查是否有冲突；如果有冲突先解决，**保留我这边的设计改动不要被基线覆盖**。我要继续在 `feature/design-花名` 分支上工作。

跑完 AI 会告诉你"已同步"或"已解决冲突"，没问题就可以继续干活。

> 💡 **小贴士**：基线分支由设计 owner 在每个工作日**早上 10 点前**同步 main 并在群里发"基线已更新"通报。所以建议**早上 10 点之后**再做这步同步，能拿到当天最新的基线。

## 五、编辑中：版本管理（重要，像 Figma 一样）

设计过程中大家会并行多个版本，且合并时可能会出现同名情况，因此必须做好版本隔离。我们用**文件夹**把这些版本平铺管理，操作和 Figma 里 V1 / V2 / V3 / 终稿是一个意思。

### 5.1 目录约定

所有探索稿统一放在 `_designer-drafts/` 顶层目录下，**第一层永远是你的英文 ID**：

```
_designer-drafts/
├── js/                    ← 你的英文 ID（jingsujiang → js）
│   ├── 登录页/
│   │   ├── v1-玻璃拟态/
│   │   ├── v2-极简白底/
│   │   ├── v3-插画风/
│   │   └── final/        ← 评审定下来这版（v3 复制过来），准备落地
│   └── 用户管理页/
│       ├── v1-表格紧凑版/
│       └── final/
├── qt/                    ← 其他同学的（qiting → qt）
└── ...
```

| 层级 | 含义 | 命名规则 |
|---|---|---|
| 第 1 层 `_designer-drafts/` | 探索稿总目录 | 固定，不要改 |
| 第 2 层 `js/` `qt/` | **你的英文 ID**（避免不同同学撞名/冲突） | 2~6 个字母小写，由 owner 统一分配 |
| 第 3 层 `登录页/` | 你正在做的页面/模块 | 中文，和实际页面名一致 |
| 第 4 层 `v1-玻璃拟态/` | 具体某个版本 | `v1-方向描述` `v2-方向描述`... 评审定下来的复制成 `final/` |

> 💡 没分配过英文 ID 的同学找 owner 要一个。分支名（如 `feature/design-jingsujiang`）用全花名，目录用缩写，两者不冲突。

### 5.2 关键约定

- ✅ **每个版本是独立文件夹**，互不覆盖，全部保留历史。
- ✅ **评审定稿时**：把定下的那版**复制**一份到 `final/`，**原 v1/v2/v3 都不要删**，方便以后回看演变。
- ✅ **正式落地时**：让 AI 把 `final/` 里的内容搬到正常页面路径下，发 PR。
- ❌ 不要在 `_designer-drafts/` 之外的地方放探索稿。
- ❌ 不要动别人的 `_designer-drafts/xx/` 目录。

### 5.3 让 AI 同时写多个版本（进阶用法）

可以让 AI 同时跑多个版本，**前提是把每个版本的产出目录写清楚**。例如开两个 CodeBuddy 对话窗，把不同版本的目录地址分别交代清楚：

> 对话窗 A："请把所有新文件放到 `_designer-drafts/js/登录页/v1-玻璃拟态/` 下，不要动其他目录。"
> 对话窗 B："请把所有新文件放到 `_designer-drafts/js/登录页/v2-极简白底/` 下，不要动其他目录。"

⚠️ **风险点**：两个对话窗如果都对同一个 git 仓库做 commit/push，会互相覆盖造成丢稿。规避方式二选一：

- **只让一个窗口管 git**（commit/push），另一个窗口只产出文件，最后由你统一在主窗口 commit；
- 或者把两个版本放在**不同的 `vN/` 子目录**，且**两个窗口都暂时不要 push**，等你检查完再统一 push。

### 5.4 版本文件夹之外的命名

如果你出于某种原因要在文件名里带版本号（比如导出截图、PRD 附件），**一定要带自己的英文 ID**，例如 `js-prototype-v1.png`，避免多人协作时同名覆盖。

## 七、改完一个节点：提交、合并冲突、推到云端

> 节奏建议：**每天对齐会议后进行提交**，下班前一定要再备份一次。
>
> ⚠️ **划清楚两件事**：
> - **「推到自己分支」= 备份**，每天都要做，不会触发任何主干合并；
> - **「发 PR」= 提议合到设计基线**，只有 final 评审通过时才做。

### 7.1 提交前再 rebase 一次（重要）

为什么还要再来一次？因为你开发的这段时间里，基线分支可能又被 owner 更新过、或别的设计同学合入过新内容。

复制这句给 AI：

> 我已经改完了，先 rebase 远程 **`feature/design-refresh-2026`** 分支（设计基线），检查是否有冲突；如果有冲突先解决，注意 rebase 后要**保留我这次的设计改动，不要被基线覆盖**。

### 7.2 情况 A：每日下班前备份（仅 push，不发 PR）

> 适用：今天没做完、半成品一堆、或者只是想存一下进度。
> 频率：**每天下班前一定要做一次**，养成习惯。换电脑、出问题想恢复都靠它。

复制这句给 AI（按 7.1 rebase 完之后）：

> 我今天先备份一下进度。把当前**所有改动都 commit**（包括 `_designer-drafts/` 下的探索稿、未完成的任何文件），commit 信息写 "WIP：5 月 13 日下班备份"，然后 push 到远端的 `feature/design-花名` 分支。**不要发 PR。**

> 💡 **WIP** = Work In Progress（进行中），是行业惯例的"半成品"标记。AI 看到 WIP 就知道这是临时备份、不打算合主干。

### 7.3 情况 B：某个版本评审通过，发布定稿（push + 发 PR）

> 适用：某个 X 页面的 `final/` 版评审通过了，要正式纳入设计基线。

按 7.1 rebase 完之后，复制这句给 AI（替换 X 页面、英文 ID 和花名）：

> 我要发布"X 页面"的定稿。请帮我做这几件事：
> 1. 把 `_designer-drafts/英文ID/X 页面/final/` 里的内容**搬到正式 X 页面路径下**（替换原文件）；
> 2. 把所有改动 push 到远端 `feature/design-花名` 分支（**包括 `_designer-drafts/` 下的探索稿历史，作为备份一并推上去**）；
> 3. 发起 PR，**目标分支 `feature/design-refresh-2026`**（不是 main），标题写 "X 页面改版（final）"；
> 4. 在 PR 描述里写明：「本次需要 review 的是正式路径下的改动；`_designer-drafts/` 是探索稿历史，不需要 review」。

> 💡 push 上去时**带 `_designer-drafts/` 是 OK 的**（你的远端备份盘可以堆任何东西）；
> PR 里**带 `_designer-drafts/` 也是 OK 的**——只要 PR 描述里说明跳过即可，owner 评审时会忽略，周合并到 main 时由 owner 统一剔除。

> 🔑 **三个分支记牢就不会乱**：
> - `main` —— 我们**不碰**，只通过 owner 周合并间接进入。
> - `feature/design-refresh-2026` —— 我们**rebase 它、PR 到它**，但不直接 push。
> - `feature/design-花名` —— 我们**自己的工作分支** + **远端备份盘**，每天下班 push 一次，全部内容随便堆，**push 不等于发 PR**。
>
> 🗂 **版本管理像 Figma**：
> - 每个版本一个文件夹，全部保留历史，互不覆盖。
> - 路径永远是 `_designer-drafts/英文ID/页面名/vN-方向/` 或 `final/`。
> - 探索稿会跟着每天的备份推到远端（保险），但**最终不会进 main**——周五合主干时由 owner 统一剔除。
